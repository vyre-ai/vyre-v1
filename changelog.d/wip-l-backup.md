- The server update backup is now consistent while the daemon writes: each SQLite database is copied with VACUUM INTO and checked, the other files are copied, and only the copy is tarred. A file that changes during the copy no longer fails the update.
- A failed backup now starts the server again instead of leaving it stopped. `vyre-server backup` takes the update lock and uses the same path as the scheduled update.
- An update that is killed or cut off now goes back to the previous release (at once on a signal, at the next command after a crash), and compose.env is rewritten whole instead of with sed.
- A lock left by a dead update process is reclaimed.
- `vyre run --env` works without a separate filler process: when VYRE_FILLER_SOCKET is not set it asks the server for each value as the caller (a person at View level), and scrubs those values from the command's output. With the socket set it reads from the socket as before.
- Two items in one folder with the same field name no longer break `vyre run --env`: the first keeps the plain name, a later one gets its item name in front (Stripe_live__api_key). If that name is taken too, the call is refused and names both items.
- `members.sso.set` now checks that the caller can use the Vault item that holds the client secret (vault.use), as connections and mail do. The item must exist in the Vault first, as the Console already does.
- `vyre-server backup` and the daily backup no longer stop the server: every database is taken as one consistent snapshot while the daemon keeps writing. Only an update stops the server for its backup.
- An update backup now also stops any container outside compose that still has the data folder mounted (named in the output), and starts it again afterwards.
- New `vyre-server restore FILE [--yes]`: it checks the file (readable, only space/ and caddy/, no links, every database passes integrity_check) before touching anything, asks for confirmation, backs up the current data, stops, restores, starts and checks health, and puts the old data back if the server is not healthy.
- `vyre run --env` never prints a fetched value, also not inside an error message from the server or a failed launch; each value fetched is a Vault use with the person as the actor.
- Vault search finds an item by name, handle, kind, field name or folder name, across Mine, Shared with me and the Space (never by a value).
- engine.accounts.list takes a place (chat, automation, agent, space) and then says for every account whether it can run there and why not, with its models, by the rule the resolver itself applies. Every picker can read the same list.
- A Space server that lost a member's key (a restart, a link that came back) gets it again from any of their open apps: the app hands the key it holds when the link is live the first time as well as after a drop, and asks every 30 seconds while open. A resumed device runs its server turns on the member's Mine sign-in whenever any device of theirs is unlocked.
- The Vault list shows Mine, Shared with me and Space as three headed sections in All and in a search. The composer offers only accounts the shared account list says can run a chat here.
- The automation "Runs on" list and its turn-on check, and the agent's AI account pickers, now read engine.accounts.list with a place instead of their own rules: an account that cannot run there is shown greyed with the reason, and the old works() and paysForAutomations() reads on providers.list are gone.
- At launch, a Space server over https that does not hold the person's key (the app was relaunched, the server restarted) shows the lock screen once, with Not now. An app that holds the key hands it over without a word, and a server that already holds it, an account with no password and a server that does not answer go straight in. Unlock in place also works from a chat on a Space server.
- A personal automation runs as its owner: any account the person may use counts for its AI steps, as before; "kept for automations" applies only to Space accounts paying for Space automations. The Space AI pickers (agent, automation, Chat key) read the same place-aware answer instead of their own rule.
- The Vault Space AI accounts tab reads engine.accounts.list too (the rows now carry what each account pays for and its provider), so the Space AI pickers and the tab share one answer.
- The shots app draws each mount after hydration, so a mount that lays itself out by the window (the Vault at 1440, the Runs on menu) no longer differs from the pre-rendered page: React error 418 is gone from those mounts.
- A live test of the launch lock on a Space server: held goes straight in; relaunched with the key lost shows the lock; Not now leaves her chat on the Space key with its one line; Unlock brings her Mine sign-in back.
