- A site's page is one page with six tabs (Overview, Deploys, Logs, Variables, Domains, Settings) under a header with its state, address and Deploy. A deploy is four steps (Fetch, Build, Start, Check), each with its time and its own lines of the log, and a row in Deploys opens it beside the list.
- A deploy that is running can be canceled: the build is cut off, a container that was started is removed, and the last good build keeps serving. A canceled deploy says Canceled and is not counted as a failure. Agents cancel with sites.deploy_cancel.
- A deploy keeps its commit's first line, so the list reads "Annual pricing on the plans page" and not a hash.
- An agent puts an app on the web in one call, sites_ship: it creates the site from its source, sets env from Vault handles, adds Postgres or Redis, deploys and waits. The answer is the address, or the step that failed with the reason and the fix, and a second call with the returned siteId goes on with the same site.
- A site's variables can be plain values as well as Vault secrets, each with where it applies (everywhere, production or previews). Paste a whole .env: its secrets go to the Vault as one item and are never shown again, the rest stay plain.
- A branch of a site's repo can be built as a preview at its own address behind Space sign-in (never public, and never with the site's databases). A new build of a branch replaces the one before it. Promote serves a preview's build as production without building it again, with the production variables; the build that was serving stays for a rollback. Agents use sites_preview_rebuild, sites_previews, sites_preview_promote and sites_preview_remove.
- Pasting a repo in New site answers before anything runs: one line for what it is and how it builds, one for what it needs (a database, variables). After a rollback, one press on Undo puts back the build that was serving.
- A cancel is recorded at any moment, including while a deploy is still reading its variables, and a deploy that was canceled never goes live afterwards. A deploy that was closed from outside is never rewritten by the job that was running it. An error after the address changed hands is reported as it is (live, with a note), never as "Canceled", and the container that serves is never removed. Canceling a deploy is now in the audit log.
- A site that comes from a GitHub repo can take GitHub's webhook: a push deploys at once (when the site deploys on push) and a branch the site follows gets its preview, and a deleted branch or a closed pull request removes it. Each site has its own secret, shown once in Settings; every delivery is checked with its signature, an unsigned or replayed delivery is refused, and nothing builds for a branch the site does not follow.
- A variable applies to production unless it is scoped wider, so a preview only gets what was scoped to it. A plain value that looks like a secret (by its name, or its shape: key and token prefixes, a private key, a login in an address, a long random string) is refused unless it is confirmed plain, here and in sites_env_set. A pasted .env is read like dotenv: quotes of either kind, values over several lines, escapes, export and comments; a key's body never becomes variable names.
- A deploy cannot be canceled once it is going live (it says so), and a stopped deploy's container is taken away. A site keeps its newest ten previews. sites_ship by name finds the site it made, and a deploy error names the deploy as the step that stopped.
- The GitHub webhook is stricter: a closed pull request from a fork never touches the site's own preview; a push that could not run is recorded as failed (the site's Settings says so) and gives its delivery id back, so GitHub's redelivery is taken again; a delivery id is kept for good, and a delivery older than what the site already handled or deployed is refused, so an old captured delivery can never put old code back. Turning the webhook off or making a new secret drops what was waiting to run, and an event that asks for nothing no longer wakes the server.
- sites_ship under a name another app of the same person already uses is refused ("A site named X already deploys Y. Pass its siteId"), never deployed over it. An agent cannot say a secret-looking value is plain (it goes to the Vault, or a person adds it on the Variables page), and sites_ship refuses one before it makes a site. Variables kept with the old default (everywhere) are left as they were and say they reach previews too.
- A captured webhook delete or closed pull request cannot be sent again to take a preview away: each delete and each close is remembered, and one is refused when the branch has had a push since the commit it removes.
- A Vault key an agent gives to a site as env (sites_ship env, sites_env_set) is held for a person unless that key was approved for that source before (the repo, or the uploaded files of that site); after a yes the pair is remembered, and the card says which key goes to which site, built from what. A person's own call is one step. Deleting a branch that was made again at the same commit removes its preview, and handled pushes are ordered by a counter that is never reused.
- One rule now covers every way a site's Vault keys meet code: an agent's call is held unless each key involved is approved for the source of that code. That covers a key added to a site's env, a site moved to another repo or files (update, deploy, plan, ship, with or without a token), and a preview promoted to production that was built from somewhere else than the site's own repo. The same source with the same keys goes through, so an agent's redeploy never waits; a person's yes is remembered per key and source, and a person's own call is one step. A build keeps where its code came from. sites.env_set has one handler.
- A site's source now has one canonical name (scheme, host, port, path with dots resolved and .git removed; only the host, and on github.com the owner and name, are lowercased), kept as its SHA-256, so two repos never share an approval. Uploaded files are named by the site and a fingerprint of the files: when an agent replaces them, the next deploy of a site that stores Vault keys waits for a person unless that exact content was approved.
