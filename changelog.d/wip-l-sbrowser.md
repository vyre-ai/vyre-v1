- Space browser: one browser service per Space host (image `vyre/space-browser`, images/space-browser) that keeps a headless Chromium per agent and per person's Assistant, each in its own profile folder on a volume, so cookies and logins never cross. A profile's browser starts when its agent first browses and stops after idle minutes; the folder stays.
- An agent's chrome_* tools now go to its own profile in the Space browser by default, with no computer needed and whoever asked, so a team agent's logins outlive the person who asked. Naming a computer, or `my-chrome` for the person's own Chrome, goes where it always went. Without a Space browser bound nothing changes.
- Vault logins fill in a profile: the host's fill channel is held by the browser for that profile's agent only, a refused handle types nothing and starts no browser, and the values it filled are scrubbed from every answer.
- The agent computer's DevTools driver (agentd chrome.ts, vault.ts) takes options (port, headless) so the Space browser reuses it; the agent computer behaves as before.
- Vyre for Chrome inside each Space browser profile is paired with the Space as that agent: the browser's native messaging host points at browserd, which serves the same bridge protocol the daemon does (lib/chrome-bridge.ts), tells the extension the Space opened it to its agent (agent.optin), and answers which Vault items fit a page, a handle to one, and the one value of a handle field, through the profile's own Vault channel. The extension's debugger permission is held from the start in this image, since nobody can grant it in a browser with no screen.
- The Vault fill channel answers two more questions for a profile's extension (`vault.items.match` and `vault.use`, nothing else) as the profile's agent for the person who asked.
- A Team server runs the Space browser behind the container runner: one container `vyre-sbrowser` on a network of its own (`vyre-sbrowsernet`) that only the ingress joins, one volume, no capability, no host folder, exec and logs only. Releases build and pin the Space browser image (images.lock `VYRE_BROWSER_IMAGE`, compose `VYRE_SPACE_BROWSER_IMAGE`), the installer and `vyre-server update` pull it, and `vyre-server doctor` says when it is not pulled.
- On a host with no container runtime an agent keeps browsing where it did before.
- Four capabilities for people to see and take over an agent's browser: `computers.browser.profiles` (the browsers you may watch, with tabs, who has the controls and whether Vyre for Chrome is paired), `computers.browser.stream` (the live view), `computers.browser.take_over` and `computers.browser.give_back`. An Assistant's browser is its person's alone; any other agent's goes to its owner and to admins; an agent never uses them.
- Who may watch an agent's browser follows how the agent is shared, by one rule in the agents module (`agents.share_class`, the same sections the Agents page uses): an Assistant, an outside agent or a personal agent, its owner only; shared with named people, they may watch and only the owner and admins take over; shared with the whole Space, its owner and admins watch and take over.
