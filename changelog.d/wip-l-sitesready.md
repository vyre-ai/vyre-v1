- Sites: Vyre now deploys an app from its source on a server of the Space, like Railway. Give a site a GitHub repo, a folder or a .zip in Files (or, for an agent on its own computer, a folder there) and press Deploy: it reads railway.json, railway.toml, nixpacks.toml, a Procfile, package.json, requirements.txt or a Dockerfile, builds the image, starts it in a container of its own and switches the address over once it answers. A failed build leaves the last good one serving. Static sites, Vite and React, Next.js, Node and Express, Python (FastAPI, Flask, Django) and any Dockerfile are built and proven live on a real Docker engine.
- Sites: each deployed site gets an address of its own (<name>.<the Space's sites domain>, or a custom domain) with automatic HTTPS from the Space's Caddy, and four kinds of access: public, Space members only (they sign in with Vyre the first time they open it in a browser, and a removed member is out on the next request), private (owner and shares) and password. Space only is the default for a new deployed site.
- Sites: env vars come from Vault keys, filled at deploy time and never shown or logged. One press adds the site's own Postgres or Redis on the server, with DATABASE_URL or REDIS_URL set, and its data survives redeploys. An existing database copies in from a pg_dump in Files or from a Vault key holding the old connection string (for example Railway's DATABASE_URL).
- Sites: deploys, rollback to any of the last five builds without a rebuild, deploy on push for a repo (checked every minute), the build log streaming while it runs, the app's own log, and every failure said in plain words with one fix button (add Postgres, add the env var, double the memory, deploy again, ask an agent).
- Sites: each site runs with a CPU, memory and process cap (1 CPU and 512 MB unless changed), rotated logs (3 x 10 MB), every capability dropped, on a network of its own, one build at a time with its own memory cap, and no build when the server's disk has under 2 GB free, so one site cannot take the Space down.
- Apps opens on Sites, and remembers the group each person had open last. New site is one sheet: a GitHub repo, a folder or zip, or Ask an agent. The Sites list shows each site's state, address, last deploy and who deployed it.
- Server operators: a new service, the sites runner, runs beside Vyre and is the only one holding the Docker socket. It speaks a narrow Docker API over a private socket with a token and refuses anything a site does not need: privileged containers, host folders, host networks and namespaces, ports, devices, capabilities, other labels or images, and exec into any container that is not a site's. `vyre-server update` adds it to existing servers and `vyre-server check` reports it. Sites get <name>.<the Space's domain> once a wildcard DNS name points at the server (Vyre detects it), or VYRE_SITES_DOMAIN. See docs/guides/move-from-railway.md.
- Sites: each site has a network of its own, joined only by its app, its Postgres and Redis, and the ingress, so a site cannot reach another site, another site's database, or Vyre (a connection from a site network to Vyre is closed). Caddy asks Vyre who may come in, then proxies straight to the site, so WebSockets work.
