## 1. Product in one page

Vyre is one app that runs on every computer (Mac, Windows, Linux, phones, web). Your computer starts as a **Personal Space**: you, your agents, your AI accounts, vault, records, files and automations, with no server and no account. A **Team Space** is a Space hosted on a server (a cloud box or the office Mac running **Vyre Server**, one command on Linux or Mac). People join it with an invite link. Only these two words are used: Personal Space and Team Space. "Node" never appears in the interface; say "your computer" and "the server".

A Space is the unit of everything. Each Space has its own keys, data, profile, Kit and an encrypted folder on every device. Nothing crosses between Spaces on its own. "Copy to Team Space" makes an independent copy of an agent, vault item or record. Connecting a server creates a new empty Team Space beside the Personal Space; it never converts it.

The work is done by people and **agents**. An agent is files and settings (AGENT.md, agent.toml, memory, skills) that live in one Space. It acts only when someone talks to it, @mentions it, hands it a task, or a routine or automation calls it. Each turn runs on the asker's own AI account (subscription sign-in or API key), on the asker's computer for private chats and on the Space server for everything shared or scheduled. Agents use secrets by handle and never see values.

People see seven kinds of thing: **chats and channels** (conversation), **records** (structured data, including projects, journeys, agents and contacts), **files** (a folder tree of Markdown and files with memory), **inbox** (every outside email, text, call and calendar item), **automations** (rules and long-running journeys), **apps** (sites, forms, campaigns, templates) and the **vault** (secrets). One composer, one task queue (My work), one approval path (the Gate), one history pattern, one Run model and one Star/Follow pair connect them.

Structure and policy live in the **Console** (console.<space-address>, owners, admins and developers). The app is for work. Everything is reachable through one typed, versioned capabilities API and one Vyre MCP; a screen, a Kit, an agent and an outside tool call the same API under the same permission check and audit.

Words: the interface says Automations, Journeys, Source rules, Needs you, servers and Engineer MCP. Retired and never shown: Flows (as a product name), Playbooks, Channel rules, Needs a choice, server nodes, Engineer agent, node, module. Prototypes and docs get one find-and-replace pass.

Design bar: local-first (a kept copy on each device, no spinners, offline works), keyboard everywhere, calm and dark-first, every element has click, right-click, hover and keyboard behaviour that changes real state, no floating toasts (a quiet line where the change happened, with Undo), no pill filters (header menus with checkmarks and counts), every place has designed Empty, Offline and Error states with one next step. Benchmark: a product Vercel, Stripe or Apple would ship (Apple fluency, Stripe simplicity, usable for hours); components are checked one by one; interaction follows Apple HIG with native menus and right-click wherever a menu exists. In any menu every item has an icon or none does. Side pane (resizable, remembers width), tab strip, viewer, menus, composer, task page, softphone, email builder and terminal are each built once in the shared UI package and reused by every place; a place may not copy or restyle them.

## 2. Primitives

Format per primitive: **What**, **Fields**, **Lifecycle**, **Permissions**, **Events**, **UI**. Permission keys are from the catalogue in section 4.12. Access levels are View, Use, Edit, Manage.

### 2.1 Space
- **What**: the isolation unit. Personal (device only, optional encrypted backup) or Team (server holds the truth; each device keeps an encrypted partial replica of what that person may access).
- **Fields**: name, legal name (shown to outsiders on forms, sites, sealed-field notices; never the word "Space"), logo, address (own domain, or relay/tunnel), hosted-on setting, defaults, Kit choice, allowed AI accounts (Any or Company only), skin default.
- **Lifecycle**: created (Personal automatically; Team by Vyre Server install); relay can switch any time with no re-invite (devices pin the Space key, not the address); leave = local folder wiped; export = owner one-click zip (never secret values, never others' private chats or personal memory).
- **Permissions**: Owner only for transfer and delete; `console.access` for the Console.
- **Events**: space.updated*, member.joined*, member.removed*.
- **UI**: Space tile and switcher (avatar menu, red dot when another Space needs you), Console Space page, Settings > Spaces.
- **Personal Space matrix**: works in a Personal Space: Chats, Records, Files, Vault, Inbox (own mailboxes), Home, Settings, and Automations that run while the computer is on (schedule, record change, manual; no webhook triggers). Needs a Team Space and shows one line "Needs a Team Space" with a way to create or join one: Apps (public sites, forms, campaign sending), Console, agent computers, webhooks, always-on runs.
- **Switching Space**: a Space is a different server, so switching swaps everything at once: data in every place (people, agents, chats, inbox, records, files, vault, automations, apps), the Space's Kit and skin, the rail (Kit-defined), your profile and role in that Space, notifications, and the title ("Vyre · <Space>"). The shell holds the current Space and every place reloads for it. A brief skeleton shows while it loads; data from two Spaces is never mixed on screen. Tabs are per device and per Space and are restored when you return to a Space. The prototype ships three seeds: the main team Space, a Personal Space (device only), and "Harbor Studio" (team, different Kit, skin and agents).

### 2.2 Principal (person, agent, outside actor, service)
- **What**: anything that can act. Person; Agent; Outside actor (registered external tool such as Claude Code or Codex, via the Vyre MCP and a token); Service (connector or webhook identity; Space automations act as services, see below).
- **Fields**: id, kind, name, owner (agents, actors, services), status, roles, groups. People: photo (Boring Avatars fallback), title, handle, time zone, working hours, away state. Agents: DiceBear Notionists face tinted per Space. Outside actors: Minidenticons identicon plus a dashed "Outside" mark.
- **Lifecycle**: person invited > accepted > active > suspended > removed (wizard with transfer preview); outside actor token: one-time (works once, 10 minutes) then registered; revoke is one click.
- **Permissions**: agents may hold any role except Owner and Admin; an agent acting for a person gets the intersection of its access and theirs.
- **Events**: principal.created*, principal.suspended*, token.revoked*.
- **UI**: Console People, Agents and actors; Records > Agents; chat faces.
- **Services and automations**: a Space automation is a Service principal. It holds roles and grants, a vault allowlist and one inference key per AI step. Its audit actor reads "Automation X, owner Y". A personal automation acts as its owner with the owner's access.
- **Declared provider**: every model and every outside actor declares its AI provider. The API checks the record's label against that provider when a tool result is returned (4.12 step 4).

### 2.3 Role, Permission, Group, Grant, Condition, Label, Policy
- **What**: the access model (section 4.12). Roles are bundles from one fixed permission catalogue (Owner, Admin, Developer, Member, Guest built in; custom by cloning). Groups are one-level sets of people and agents. Grants give a person, group or role a level (View, Use, Edit, Manage) on a resource, flowing down, with optional conditions (row filter, hidden fields, label ceiling, time window, expiry). Labels (Public, Internal, Confidential, Restricted) cap what a role's clearance may open and which AI providers may receive the data. Policies (Gate rules, spend, retention, sign-in, sharing) apply last.
- **Lifecycle**: role changes stage as a diff showing who gains or loses what, then Apply. Built-in columns are locked except to clone. A role cannot be deleted while held.
- **Events**: access.changed*, grant.created*, grant.revoked*, policy.changed*.
- **UI**: Console Access group (People, Groups, Roles matrix, Grants, Policies, Access checker, Access reviews, Sessions and devices); every share sheet.
- **Access levels, one vocabulary everywhere**: View, Use, Edit, Manage. Vault: Use = fill without seeing; View = see the value (reveal, logged); Edit = change fields; Manage = share and delete. Automations: View, Edit, Manage (the accountable owner holds Manage).
- **Everyone group**: a built-in group "Everyone" with admin-editable default grants (Kits ship defaults). Invites add the person to groups, so a new Member sees something on day one.
- **Field permissions**: edited in the Console on the record type. A field permission is a hidden or read-only condition on a record-type grant plus a label on the field. Labels inherit from the container unless set on the item.
- **Guests**: explicit grants on records, folders and read-only shared links only; channels are internal only (a client portal is a site built on the API, 3.6).

### 2.4 Resource and folder
- **What**: anything access applies to: record type, project, folder, channel, inbox, vault folder, automation group, agent, connector. Every list of things you make (sites, forms, campaigns, automations, agents, record types, vault items, channels, runbooks, terminals) is organised the same way: Personal, Shared with me, Space; folders with counts; one share sheet. A folder's sharing covers everything in it; you see only what is shared with you. The interface says "folders"; "Groups" means groups of people in the Console.
- **Lifecycle**: new items start Personal. Moving an item into a shared folder shares it. Trash restore applies.
- **Events**: folder.shared*, item.moved*.
- **UI**: sidebar sections in every place; share sheet.
- **Record-level grants**: a record is a resource that inherits from its record type and can carry its own grants. Project roles write grants: Lead = Manage, Member = Edit, Reviewer = View plus Edit on tasks assigned to them, Guest = View.
- **Starred, Following and Shared with me** are lists over the same resources; none is a second place to store things.

### 2.5 Chat, Channel, Thread, Message
- **What**: **Chat**: one person with any number of agents, or exactly two people (a DM). A third person always means a new channel; agents do not count toward that. **Channel**: a named lasting room with any mix of people and agents, public to the Team Space or invite-only. **Thread**: inline replies under any message; an @mentioned agent works in a thread. Each thread is one session underneath (the word "session" is never shown).
- **Fields (message)**: author (person, agent, outside actor), body, attachments (land in the channel's folder), reactions, edits, pinned-message marker (a content marker, not a Star), blocks (native blocks only), source links.
- **Lifecycle**: a private chat never gains people: @mentioning a person offers "Start a channel with them", a new channel linked back. Agent work lives in the agent's own thread (a normal chat component) that stays open until done, stopped, or idle with nothing waiting; it can wait in the background ("Waiting on: build 42") and wake in the same thread.
- **Agent modes per thread**: each agent is Leading (answers every message that is not addressed to a person with @, and shows "Intake will reply"; one lead per thread) or Listening (costs nothing until invoked: it is included in context when asked and runs no inference per message; replies only when @mentioned or asked). Defaults: chat or Ask thread with an agent, or a thread an agent started: that agent leads. Channels and human threads: agents listen. Agents act unmentioned in a channel only when "watches this channel" is on, logged like a routine.
- **Permissions**: `channels.create`, `channels.agents` (invite agents), `chats.private`. Channel access is a grant on the channel.
- **Events**: `message.received`, message.edited*, thread.started*, agent.engaged*, agent.handoff*.
- **UI**: Chats place; side tabs; thread header with faces and mode marks.
- **Hop and loop limits** (defaults, configurable in Policies): agent-to-agent hops 4 before a person must reply; review loop 2 send-backs; CI fix loop 3.
- **Ask panes** are private chats scoped to an object. They live in that object's pane history and appear in Recent only after "Open as chat". Same account and memory rules as a chat.
- **Project and Journey channels** appear in the Chats sidebar only if you are a member and have starred or followed them, in a "Projects" group inside Channels. They archive when the record completes.

### 2.6 Agent
- **What**: a default record type (beside Projects and Journeys). One agent is one record, one folder in Files (Agents/<name>), one name in Chats. Made by chatting with your assistant using the create-agent skill, ending in one Approve card. "New agent" in Records and Chats both start this chat.
- **Fields**: face, name, role/"use me when" line, status (Awake idle for 2 min, Working, Asleep, Paused with reason and who), owner, access (who can chat, who can change), model and fallback, whose account runs it, tools allowed/denied, vault key names, limits per run/day/month (spend, turns, time; money caps apply to API keys, subscriptions are capped in turns, time and token counts), memory capture mode, computer (Team Space only), watchers, routine schedules set by the owner, handoffs, template version.
- **Files (decided tree)**: AGENT.md (people write, agent proposes diffs; under 150 lines), agent.toml (owner writes; app validates and enforces), memory/ (MAP.md under 200 lines, notes/, proposed/, recipes/, journal/YYYY/MM/DD.md), skills/, routines/, knowledge/, inbox/, work/ (drafts/, done/, scratch/), downloads/, logs/ (app-written, read-only), chats/ (encrypted transcripts, search only), .vyre/ and .index/ (hidden). Space level: VYRE.md (admins write; under 120 lines; at most 8 hard rules), shared knowledge/, Agent template. Vyre's own text is .vyre/guide.md, rewritten by app updates. Precedence: app limits, agent.toml, the person's message, AGENT.md, VYRE.md. Memory and skills are information, never authority. AGENT.md may narrow VYRE.md and loosens it only with an `Override:` line.
- **Lifecycle**: a run uses a snapshot of its files; changes apply between runs; a broken agent.toml keeps the last good version running and shows an error. Every save of VYRE.md, AGENT.md and agent.toml is versioned (rollback). Template propagation: add never remove, never overwrite, changed files are suggestions; preview first ("12 agents, 3 folders added, 2 suggestions"), "Apply to one agent first", widening suggestions need Space admin approval; per-Space switch Suggest (default), New agents only, Off.
- **Permissions**: `agents.create`, `agents.manage`, `agents.schedule`, `computers.use`. Agents, Projects and Journeys show only those you are in or that are shared with you; admins toggle "All in the Space" (logged). Private agents' folders are hidden from others. Accept on an AGENT.md change is shown only to owner and editors; others see "Suggest to <owner>"; personal preferences go to the asker's private memory, never AGENT.md.
- **Events**: agent.created*, agent.paused*, agent.limit_hit*, agent.config_changed*.
- **UI**: agent record page (face, name, role, status; Chat, folder, computer as icon buttons; strip of chats this week, open tasks, runs today, spend against limit, memory facts, proposed facts; Working on; Linked; Routines and watchers; Access; Keys; Setup), Chats pinned faces, Files tree, Console Agents register.
- **Role line and routine labels**: the role line under an agent's name edits in place; Enter saves to `description` in agent.toml with an inline Undo; people who cannot change the agent see it read-only with a lock on hover. Messages and posts an agent makes because of a routine carry a line "Sent by <agent> on a routine <person> set"; nobody else sees or edits the routine.

### 2.7 Agent computer, Terminal
- **What**: Team Space only. One sealed container per agent on one host (a server, or a Linux VM on a Mac), headless Chrome by default, full desktop on demand (Computer tab, Take over, or the Screen tool), sleeps when idle and never mid-task, tab limits, none unless the agent needs one. Logged in once; stays signed in. Files tool: the agent's Files folder is mounted as ~/Vyre (one copy, no sync). Vyre for Chrome is installed in it, signed in as the agent.
- **Tools**: Chrome, Terminal, Screen, Files. Thinking happens where the chat runs; actions happen on the server.
- **States**: Asleep (last frame dimmed, Wake), Working (live scaled view, caption), Take over ("You're in control", Give back; your actions become one "You took over" step). Pop out = Screen Share view.
- **Terminal**: a tab (hosts: agent computer, Space server, your computer). A session survives its tab; an agent's commands show as one step "Ran 4 commands on Intake's computer" with "Open terminal" attaching the same live session; leftover scripts are named sessions; star one to put it on Home. Server shell needs `server.services` (locked state with Ask for access otherwise).
- **Personal Space**: no agent computer; a browser-needing agent uses the Chrome extension on your Chrome; its terminal is locked to the Personal Space folder plus folders you add, with allow/ask/deny rules.
- **Events**: computer.started*, computer.slept*, computer.takeover*.
- **UI**: agent pane Computer tab; session timeline (frame per step; Show This Step, Copy Caption, Make a Skill from Here).
- **Access and storage**: `computers.use` is split into watch and take over. Profile disks (signed-in browser sessions) are encrypted with the Space key, and the signed-in sessions are listed under Sessions and devices.
- **Record while you take over**: a Record icon sits beside Give back. Recording captures every click and key with the element, each page visited, all network traffic (requests with timing, bodies with secrets masked) and a full video of the screen. When you stop, one sheet asks what the agent should do with it, any of: make a skill from it; learn a routine (replayable steps); work out the app's backend calls (the network log becomes a recipe the agent can call directly, stored as a site recipe note); learn this person's workflow in this app and repeat it as it is. The recording is stored in the agent's folder (`work/recordings/`), shown as one step "You recorded 4 minutes" in the timeline, and follows the folder's access. A second icon opens the agent's chat beside the full-screen computer.
- **Computer popup**: in the agent pane the computer shows an idle or sleep animation (a working agent shows a tiny live view with a typing cursor). Click opens a popup covering about 90 percent of the window with the rest dimmed; Esc or the close icon dismisses. The only controls are icons on the side: Take over (flips to Give back), Record, Chat and Close.

### 2.8 Task and Request
- **What**: one task primitive. Kinds: Work (default), Approve, Review, Answer, Unblock, Signature (waits on an outside signer). A Request (what Needs you shows) is a task of kind Approve/Review/Answer/Unblock.
- **Fields**: title, one-line summary, why, content blocks (table, document excerpt with filled values marked, diff, file, record card, screenshot, form fields, checklist), actions offered, source (chat or run), Assigned, Reviewer, Approver (each a person, agent, group, role or automation), due, effort, status (see States), links to records and files, working notes (key/value, any person or agent), followers, thread.
- **Lifecycle**: created four ways: a gated action stops and becomes Approve with the exact preview; a Journey/Automation task reaches its Reviewer/Approver slot; the agent asks with its request tool; the agent is blocked (login, key, site down) and says what would unblock it. Acting in Needs you acts at the source: approving continues the chat or run at once; Send back carries the note in. Snooze returns at its time; handing over moves it to the other person's list with the note. Status lives in the circle at the title (menu on click, Space toggles done). Review loops: a reviewer agent may send work back twice (default), then a person decides; the owner's floor can require a human approver. Plain @mentions never create tasks; the Task button (or T in an empty composer) picks the assignee first, other @mentions become followers.
- **Permissions**: any task is visible to its participants and to those who see its parent record. Gate-kind Approve tasks arrive from Policies.
- **Events**: task.created*, `task.completed`, task.sent_back*, task.approved*, task.escalated*.
- **UI**: the shared task page (one component everywhere, with a Journey bar when part of a Journey), Home My work, Needs you (filter), Plan, record Tasks.
- **States**: To do, Doing, In review, Awaiting approval, Done, Canceled. Blocked is derived (an open Unblock child task or an unmet dependency), never set by hand. Transitions: reviewer send-back goes to Doing with the note; approver reject goes to Doing with the note; approve goes to Done. Requests created by agents or the Gate start at Awaiting approval (kind Approve) or Answer and close when acted on.
- **Assignees**: person, agent, group, role or Automation. A group or role assignment shows to every holder; the first "Take" locks it and others see "taken by". Reviewer and approver may not equal the assignee unless the Space policy allows it.
- **Needs you** shows my tasks that are Ready of kind Approve, Review, Answer or Unblock, or due today or overdue, or blocking another person, agent or Run. A request is withdrawn with a note when its source chat or run is stopped or the item changed. A request addressed to a role is resolved by the first action; others see "handled by <name>".
- **Delegation never widens access**: if the delegate cannot act on an item it passes to the next delegate or the role; the delegate sees only the request's blocks.

### 2.9 Record type, Record, Field, View, Relation
- **What**: SQLite store, local-first. A record is a page, not a form. Record types are created and edited in the Console (native and synced). Agents, Projects, Journeys, Contacts, Companies, Meetings, Pull requests and Issues are record types.
- **Field types**: text, rich long text, number, money (multi-currency), date/time (zones), duration, choice, multi-choice, status, checkbox, rating, person, email, phone, URL, address, relation (two-way), lookup, rollup, formula, auto-number, created/modified (time, by), files, signature, sealed, button (runs an Automation or asks an agent), AI field (agent fills from other fields, with a source).
- **Field rules**: required, unique, defaults, validation, lock after an approval.
- **Views**: table, board, calendar, timeline, gallery, list, map, form, charts. Saved views (filter, sort, group, hidden fields, colour rules), personal or shared.
- **Page**: title and one-line summary (AI field may write), two-column sheet edited in place, foldable sections, no Save button, Undo inline; right pane = activity, comments with @mentions, its chat with any agent, files, memory facts; relations as linked cards with hover peek; `[[` links a record anywhere; related lists with totals; relationship map (two hops); completeness ring ("8 of 11", "Ask for these"); lookup paths on hover. Admin sets the layout; each person folds sections and keeps fields visible for themselves.
- **Lifecycle**: trash with restore (30 days), retention rules per type, holds block delete/expiry. Schema additions go straight through; destructive changes (delete or retype a field, drop a type) show a diff to confirm. Import from CSV, Excel, Airtable, Notion, Google Sheets; export to CSV/Excel (permissioned). Duplicates found and merged (a merge keeps all history).
- **Sealed fields**: encrypted with the Space vault keys, never plain in SQLite; agents get a handle `rec_<tableId>_<recordId>_<Field>` (ids are lowercase alphanumeric, at most 6 characters) shown as `rec_...TaxID`, middle hidden on hover with Copy. Reveal asks once and is logged per actor. Masked in search, exports, history, memory and AI context. A sealed field on a form is encrypted in the browser. Sensitive or sealed fields may require a one-time code on forms.
- **Agent-filled values**: always carry a source and time; per field either review before they count or straight in; "Needs review" view per type; source popover on each value.
- **Speed**: 100,000-row table opens under 100 ms; search under 50 ms; edits instant, synced behind.
- **Permissions**: `records.create/edit/delete/export/reveal/hold`, `schema.manage`; per-record and per-field via grants and conditions; agents see handles only.
- **Events**: `record.updated`, record.created*, record.deleted*, record.merged*, field.revealed*, schema.changed*.
- **UI**: Records place; record page; Console Schema.
- **Button field**: runs as the Space automation, "started by <clicker>". The clicker needs Use on the automation and Edit on the record. The Gate applies. A personal automation runs only for its owner.
- **Merge**: the merge sheet picks a survivor and a value per field. Relations, Journeys, channels and followers repoint to the survivor. Synced records are linked, not merged. A merge is undoable for 30 days and needs `records.delete`.
- **Form answers vs agent values**: form answers carry source "link holder" and skip review; sealed and sensitive fields need the code. "Needs review" shows per type and counts into My work for the field's reviewer role.
- **Fields on the page**: a person "keeps fields visible" (the earlier "pin fields"); this is a personal display choice, not a Star.

### 2.10 Source, Connector, Connection, Synced type
- **What**: **Source**: a way outside events become records (Zoom, Gmail, Google Calendar, Stripe, QuickBooks, generic webhook with mapping). One pipeline: connector per source, verified endpoint `/hooks/<source>`, dedupe on provider id, normalise, upsert through the primitives API, one shared linking step (sure matches link, unsure go to Needs you). **Connector** = the kind; **Connection** = one account plugged into it (many per connector; owned by a person or the Space; scoped; pausable by its owner). **Synced type** = a normal record type with a sync binding and a local mirror.
- **Sync modes**: two-way ships in v1. Every remote field mirrored; each field has a direction: Pull, Push, Both or Off. Per type: create at source (on/off), deletes travel (off by default), conflict rule for Both (newest wins, source wins, Vyre wins, ask me; default newest, but for sensitive-matching fields default Off and conflicts default "ask me"). Outbox with idempotency key, retries, "pending" mark, stored replaced value so any push can be undone, dry-run preview ("will update 34 records in HubSpot"). Match rule on first sync. Transforms as small expressions. Change detection: webhooks, cursor polling (2 min in use, 15 idle, 1 h dormant), nightly reconcile; own writes stamped. Deletes soft ("Removed at source"), pause and ask if more than 10 percent or 50 records vanish. Schema watched ("3 changes to review"). Add-on fields, notes, files, comments, tasks and relations live on synced records and are never pushed. "Make this native" detaches and keeps ids, history and attribution.
- **Connector framework**: a folder `connectors/<app>/` with connector.toml, optional transforms.js, tests/ with recorded responses, README. Secrets by name only; runs sandboxed on the Space server with network access only to the app's domains. Built by asking ("Connect Lawmatics" runs the build-connector skill: reads docs, drafts, asks for a key via a Vault request, runs the harness, shows results) or from outside via CLI/MCP (`vyre connector init/test/run/publish`). Updates show a diff and a fresh test run; a failing test keeps the last good version live. HubSpot is the built-in example. Export a connector as a folder; no public gallery in v1.
- **Mail and calendar**: sync not webhook (authorise once, push notices plus change cursor); the same message through several inboxes is one record ("in Maya's and Omar's inboxes"); a connection files only mail with contacts that match records; the inbox owner can mark any message private (kept out of the record). A calendar event and a Zoom meeting for one call merge on time plus attendees or link into one Meeting.
- **Events**: source.received*, sync.completed*, sync.conflict*, sync.push_failed*.
- **UI**: record type header (sync line, menu: Sync now, Pause, Mapping, Log, Reconnect, Make this native), record footer "Synced from HubSpot, 4 minutes ago", Console Integrations, Sources page on every record type.
- **Sync conflict card** shows base, theirs and ours with timestamps and actors, the direction rule that fired, and "Replay on a copy". The pull and push pair is logged under one trace id.
- **Imports, backfill and bulk upsert** fire no automations unless the importer ticks "run automations" (default off).

### 2.11 Form
- **What**: a view of a record type (every input maps to a field; uploads to file fields; validation and sealed handling carry over). Lives in Apps > Forms. Kinds: public link, one-use generated link (Forms API: short-lived per-record form from a gap check, asks only missing fields, can expire or be single-use, partial answers save, answers write to that record with the person as source), booking page (calendar, length, buffer, questions; creates or updates a record and a meeting), survey (form plus rating/choice and a results view).
- **Fields per form**: per field Ask, Show read-only or Hide; prefill and hide by URL key; signed record links (no emails in URLs); layout, theme, fonts, custom CSS, cover images, multi-step, conditional logic, thank-you page or redirect; consent text, captcha toggle, upload size/type policy; rate limits on form and /hooks endpoints.
- **Attribution**: every form tracks UTMs, click ids, ad cookies, referrer, landing page, device and location with no setup (consent-aware). People and client records keep First source and Latest source (source, medium, channel, campaign and more); editable "Source rules" (channel rules); a campaign link builder.
- **Events**: form.submitted*, booking.created*.
- **Permissions**: answers count as from the link holder; embeds in sites; an Automation can trigger on submit.
- **UI**: Apps > Forms list (name, record type, link kind, state, submissions) with settings pane.
- **Match rule**: each form has a match rule (email, phone or a chosen field), default upsert on email. Unsure matches go to Needs you. First source is set only on create. Attribution is a field group any record type can enable, on by default for Kit lead types.
- **Targets**: a form on a site must write to a Space record type. Site tables are for app data (2.20).
- **Booking pages**: a page has a host (a person, or a role pool with round robin). Availability comes from connected calendars. A disconnected host makes the page show unavailable and alerts the owner. Times show in the visitor's time zone.

### 2.12 Automation, Journey
- **What**: **Automation**: runs on its own in seconds or minutes. **Journey**: one piece of work lasting days or weeks, moving through stages with tasks for people and agents. One engine underneath both and Campaigns: same task (Assigned/Reviewer/Approver), per-step inference key and backup, one chat per run, triggers, audit.
- **Automation**: Personal (yours alone; runs with only your access) or Space (named accountable owner, handed off; View/Edit/Manage, editors are equally owners; followers; escalation to a role; per-automation error alerts: who, when (every failure or after N in a row), where (Needs you, DM, channel)). Promote to Space keeps history and versions, runs on access granted to the automation itself (it is a Service, 2.2), and shows that access as a diff to confirm; a subscription key on an AI step must be replaced with a shared API key on the promote sheet; "Make a personal copy" goes the other way. Canvas editor: several triggers, Paths, Parallel, Wait, Loop, Approval, Stop, per-step error handling; Runs light up the lane taken; Groups in the sidebar. Durable log per step; retries with backoff and idempotency keys; test mode with sample data; versions; run history with replay; failed-runs inbox.
- **Triggers**: schedule, webhook, record change, form submit, email received, chat message, plus spreadsheet row added/changed, CI check, meeting transcript ready, Journey stage entered, campaign reply, button.
- **Steps**: plain steps, AI steps (an agent with Assigned/Reviewer/Approver, timeout, nudge, escalation), spreadsheet steps (Create, Add rows, Find rows, Update rows, Delete rows, Read all rows), send, create task, start a Journey, wait for a Journey stage.
- **AI step key**: each AI step and each agent Journey task picks an inference key (your subscription sign-ins and API keys shared with you) plus a backup; the run chat records which key and model ran. A lost key falls back to the backup, then the run waits in the owner's Needs you to pick a new key; it never fails silently. Settings > Alerts shows the escalation chain ("Maya, then Admins after 4 hours").
- **One chat per run**: every agent does its step in it in order; plain steps are compact rows; AI steps are full agent turns; reviewers and approvers join at their step; parallel branches are side threads; an agent sees its step's inputs and earlier outputs, and may read the whole run on request, scoped to what the Automation can see, logged in the run chat. Found in the Automation's run history and the agent's "Automation runs" button, never Recent unless it waits on you.
- **Journey**: designed in Automations (stages, tasks, who does them, the automations each stage runs; needs `journeys.manage`). A Journey has a required Subject relation to another record type (the lead, the case) and a Start rule (an event plus filter) compiled to an Automation. Creating a Journey creates its record type through a controlled path that needs only `journeys.manage`; extra fields are added in the Console. Each Journey is a record type cloned from the Projects template (ordered stages, lead, client, dates, health, budget, tasks, Board and Timeline views), its own fields added in the Console. Each record has its own channel and folder. Joined to Automations four ways: stage entry runs an Automation; an Automation step starts a Journey; a Journey task can be done by an Automation; an Automation can wait for a stage. Stage exit rules, manual moves and time limits: Provisional (b3): a stage advances when its required tasks are done; designers can move a record by hand with a reason; a stage time limit breach reaches the owner's Needs you, then the escalation role; handoffs post in the record's channel.
- **Permissions**: `automations.personal`, `automations.space`, `journeys.manage`, `campaigns.launch`.
- **Events**: automation.run_started*, run.failed*, journey.stage_entered*, `task.completed`.
- **UI**: Automations place (Automations and Journeys tabs, Groups); Records for Journey records.
- **Trigger model**: a trigger is an event subscription plus a filter, or a schedule, an inbound webhook, a manual start, or a button. Record-change filters can name fields. Import, sync backfill and bulk upsert fire nothing unless the importer ticks "run automations" (default off).
- **Versions**: a run pins the definition version at start. Replay offers "same version" or "current". Journey definitions are versioned; in-flight records stay on their version until a Migrate step with a stage mapping preview. A stage in use cannot be deleted.
- **Waits and schedules**: every wait has a timeout (default 30 days) and cancels when its subject record is deleted or leaves the stage. Each schedule has "if missed": skip or run once; default run once if within 1 hour, else skip with a note in the owner's digest.
- **Step errors** use the shared error shape (4.18).
- **Self-trigger**: an automation does not retrigger on events whose origin is itself unless "allow self-trigger" is on; chain depth limit 8.
- **Workspace rule**: only Projects and Journey-derived types get a channel, folder and plan. Anything else that needs them is created as a Journey type. There is no per-type workspace setting.

### 2.13 Run
- **What**: one model for flow runs, routines, campaigns sending, deployments, runbook runs, agent background waits and terminal sessions.
- **Fields**: owner, status (Queued, Running, Waiting for approval, background work or a key, Succeeded, Failed, Stopped), log, cost, started by, retry, stop, key/model used, run id (every write of an agent run is grouped under it; "Undo this run" on the run chat).
- **Lifecycle**: failed runs of any kind land in the owner's Needs you. A run that acts on a record with a channel posts its own thread in that channel (status, one-line result, steps as the thread, approvals and retries inline; repeats collapse; a quiet menu shows People, Agents or Runs), so a project's or Journey record's channel is its full timeline.
- **Events**: run.started*, run.waiting*, run.succeeded*, run.failed*, run.stopped*.
- **UI**: run history on each Automation/agent/site; Console single Runs view.
- **Control and visibility**: stop and retry by the owner and Manage holders. People see their Runs in Home > My work > Runs and on each object; the Console shows all.
- **The run chat is the thread**: one object, shown in run history and, if the record has a channel, in that channel. High-frequency runs collapse to one summary row per N runs. Retention follows the "run logs" default (2.26).
- **Waiting**: a multi-day wait that outlives the starter's subscription token posts an Unblock to the starter, falls back to the agent's backup key if set, and the Run shows Waiting, not Failed.

### 2.14 Gate
- **What**: one approval model for every outward or risky act: send, post, pay, delete, push to a protected branch, campaign launch, secret export, promote to production. Rules are set in the Console Policies (Space default, per-agent overrides in agent.toml: approvals with timeout and what happens on timeout). It arrives as an Approve task with the exact preview.
- **Rules**: an agent send passes the Gate (preview then approve, or the agent's rule allows it). Auto mode skips the personal ask before outward sends unless the owner's floor marks them always-ask; every send is logged; "Drafted by an agent" label on outward messages is on by default. Always-ask in Auto: deleting outside work/, sending money or submitting a card, anything the floor marks. Approvals still waiting after 4 hours send one email as a backstop. Evaluation order: Ask, Allow and Auto govern only local tool prompts (terminal, Chrome) and cannot loosen the Gate. The effective rule is the strictest of Space policy, owner floor and agent.toml. The Gate applies to acts by agents, automations and campaigns, plus human launches of campaigns, promotes, protected pushes and exports. Ordinary human sends do not pass the Gate (no friction on people's own acts). Approvers for Gate acts must be people unless a Policy names an agent for a low-risk kind. Timeout default: the act is not sent; it escalates to the approver's delegate or role after N hours, with an email backstop at 4 hours.
- **Events**: gate.requested*, gate.approved*, gate.denied*, gate.expired*.

### 2.15 Memory (note, fact, layer, graph)
- **What**: every Space is a folder of Markdown. Every fact is **bi-temporal** (when true; when learned), has a **source** (the person whose message it came from or on whose request the agent worked, or the Automation/Journey run, plus a link to the exact chat, task or record) and is never overwritten: a change closes the old fact and adds a new one. Records and chats appear as notes in the graph.
- **Layers**: your personal memory per Space (stored under People/<person>/memory/<agent>/, encrypted under your key, outside the agent folder); the agent; a project; the whole Space. The layer toggle shows "Personal layers are private". A chat reads from the layers it may read; nothing is copied between them.
- **Capture**: at chat end new facts go to the person's own layer of the agent's memory (propose mode). When the agent judges a fact belongs to the team, the person whose data it is gets a promotion request to the agent's shared memory or the project/Space memory; if that person can also edit the agent, their approval is enough, otherwise it goes to the agent's owner. Promotion carries their name and time; no admin involved; shared memory is versioned (owners/admins restore; any promotion can be undone). Low-risk fact kinds merge on their own; the rest wait in memory/proposed/ with a weekly nudge. Nightly: merge accepted facts, close old versions, rewrite MAP.md. Engines' own memory is switched off: one memory.
- **Loading**: every chat loads .vyre/guide.md, VYRE.md, AGENT.md, MAP.md. Every message adds a pointer block from a local lookup (no model call, 20 to 50 ms): up to about 5 lines (note title, the one current fact with "true since", path), capped at 300 to 400 tokens, in the user turn (never the system prompt), nothing repeated, none for short acks or mid-tool-loop steps. Tools for depth: `memory_search`, `read_note`, `facts_as_of(date)`; transcript search returns snippets with links, never raw files. Thresholds are tuned by the 50-question proof set.
- **People control**: "From you" filter on every agent's Memory tab; correct a fact (old one closed with today's date) or remove it (closed off from answers, kept in history), one at a time or all at once; "Erase completely" is separate, open to the source person or an admin, deletes from history, audit entry records who and when, never what. Teammates see facts they may see. A team agent may search other people's channels, threads and shared chats; snippets include only what you may see and link to source. Private 1:1 transcripts are never searched by others.
- **Graph**: nodes are notes (people, clients, projects, sites, decisions) plus records and chats; edges are links, relations and "came from"; one colour per kind across Spaces; clusters named after their hub; saved positions; built per viewer through access checks; time slider ("what did it believe on 3 March"); WebGL (sigma.js, graphology). Per-agent graph is the default; Space-wide is one toggle; admins can open an "everything" view, logged. It covers agent, project and Space layers only, never personal layers. Export excludes personal layers.
- **Events**: memory.fact_proposed*, memory.promoted*, memory.removed*, memory.erased*.
- **Who accepts what**: facts from channel messages are already shared and go to the project layer directly with their source. Facts from private chats go to the person's layer and need their promotion approval. Facts from Automation runs go to proposed/ for the agent owner. Low-risk kinds auto-merge.

### 2.16 File, Folder (Files), Version, Mount, Changeset
- **What**: the Space as one folder tree (Agents, Projects, People, Channels, shared knowledge, Agent template (admins), Deployments/, GitHub/; Recent, Shared with me, Trash; Memory and Graph under Knowledge). One viewer and editor for every file type, full size or as a side tab; Find inside every file. Finder-grade interaction (select, drag, spring-loaded folders, Quick Look, Trash 30 days).
- **Versions (One History)**: every file keeps versions; any folder can be a git repository (local history automatically, optional remote). History = list of versions with who and why, compare as a diff tab, restore. Same pattern for records, Automations, memory, Kits and agent definitions.
- **Mounts**: a Google Shared Drive/folder, a SharePoint library/OneDrive folder, a folder on your computer, or a GitHub repository (a real clone: branch picker, pull, push, sync, commits with authors, open PRs linked). Appear as normal folders with a source mark and sync both ways; agents work in them like any folder. Access never widens: you open what the provider lets you, narrowed by Vyre grants. A local folder mount: Provisional (b17): private to you by default, shareable; contents sync to the server so it stays available when your computer is off (marked "from Irfad's MacBook"), or choose "Live only" (read only while your computer is online, no server copy).
- **Diff tab**: a commit, a PR, two versions, or an agent's working changes. File list with counts, unified or split, word marks, paragraph diff for docx/md, side-by-side or slider for images, inline comments with @ people and agents (an @ agent answers in the thread), revert a single change, keys j/k n/p Cmd-Enter.
- **Changeset**: agent edits become "Docs changed 3 files, Review": Approve and commit, Request changes (unsent comments go to the agent's thread), or Discard. Review with... an outside agent (Claude Code, Codex). A push to a protected branch raises a Gate line. Working-copy changes of a git folder use the same header.
- **Runbooks**: markdown with fenced sh/bash blocks that get Run buttons and a "Runs on <server | agent computer>" bar plus Run all; output inline; every run kept in History (who, where, when, exit, duration); Run all stops at the first error.
- **Spreadsheets**: native CSV/XLSX, Google Sheet in a mounted Drive folder, Excel in SharePoint/OneDrive work as table files for steps and a row trigger; every write is a version labelled with the automation and run; rows are appended or updated by row so two runs never overwrite; provider writes show live to people with the sheet open.
- **Folders for work**: `#` in a chat with an agent picks its working folder (Provisional, b16: one `#` picker, Folders group first in a chat with an agent, Channels first in a channel or chat with people; picking a folder shows a chip above the composer).
- **Permissions**: `files.write`, `files.delete`, `files.share_external`; folder grants flow down. Agents see only folders they may (their mount shows only what that agent may see).
- **Events**: file.created*, file.version_added*, changeset.opened*, changeset.approved*, folder.mounted*.
- **Binary conflicts**: the newest save is current; the other is kept as a labelled version and listed as a Conflicts row. Native Google Docs, Sheets and Slides have no bytes: they open as an export snapshot, with edits through the provider API (Docs, Sheets) and "Open in Google" for Slides.
- **Review changes**: folders with "Review changes" on (default for git repos and mounted cloud folders) stage agent writes in a working copy that syncs only on Approve. A changeset records its base version and 3-way merges on Approve, sending conflicts to the reviewer. The reviewer is the asker or the step reviewer.
- **Separation of duties**: the person who asked an agent can approve its changeset, but a push to a protected branch needs an approver holding push right; "different person" is an option. A failing check "Ask author agent to fix" loops at most 3 times.
- **File version retention**: see 2.26.
- **Viewer and markup**: image files show thumbnails at a good size (grid) and open in the same viewer; documents, CSVs and anything an agent delivers inline open in that viewer, not a copy. The viewer takes the shared side pane so a chat with its agent sits beside the file. Images can be marked up: Draw (freehand) or Comment on an area (drag a box, type a note); notes are numbered pins the agent reads. Plans and documents support inline editing and highlight-and-comment.

### 2.17 Vault, Item, Handle
- **What**: items are a name plus KEY=value fields (like a small .env): logins, API keys, cards, notes, passkeys, TOTP. AI providers sit at the top. Mine and Shared, with folders. Any import in one step (1Password, Bitwarden, LastPass, Chrome). Password generator, rotation reminders, team health (weak, reused, stale; breach checks deferred).
- **Use by handle**: every person and agent is a registered actor; the vault decides who has what. An agent asks the vault and gets a handle like `#Dana_Lawmatics`, never the value; the value is filled in mid-call and scrubbed from results. Fill-in happens wherever the session runs: your computer (a separate vault process the agent cannot touch; the call leaves from your IP) or the Space (when the session runs there). An owner can lock an item "Space only" (always filled on the Space). Agent computer logins stay on that computer.
- **Levels**: Use (fill without seeing), View (see the value, reveal logged), Edit (change fields), Manage (share, delete). Agents get Use only. Reveal asks once and every use is in the item's history.
- **Export**: default is injection (`vyre run --env folder -- command` puts values into that process only). A .env file is the permissioned exception (`vault.export`, high risk; Owner and Admin on; Member and Guest off; Developers only on folders granted; per-folder Who can export; never for Restricted items; file pull expires after 1 hour, 1 day or 7 days; every export audited, folder owner notified).
- **Sealed record fields** use the same mid-call fill-in.
- **Events**: vault.used*, vault.revealed*, vault.exported*, vault.requested*.
- **UI**: Vault place; Chrome extension; Console vault policy.
- **Encryption split**: Mine items are encrypted under the person's key. Shared items and sealed fields are encrypted under the Space key and decryptable only by the vault service at fill time; never indexed, never logged. Env values used by a site must allow "inject into deployments".
- **Requests**: a missing key requested by an agent or skill goes to the folder's managers and the requester sees its status.

### 2.18 Inbox, Mailbox, Number, Message (outside), Meeting
- **What**: Inbox is the place for every outside conversation. Many inboxes: each person connects their own mailboxes (Gmail, Outlook, IMAP) and Twilio numbers; agents get their own addresses and numbers; the Space has shared inboxes (hello@, support@) with owners and members. Each mailbox chooses private, shared with the Space, or shared with chosen people. Google Workspace and Microsoft 365 are built in through admin consent (domain-wide delegation / app registration), mapping members by email, always acting as that person, every call audited, a member can be excluded. Domain-wide delegation grants the capability only. Each member's mail and calendar connection starts Pending. The Space policy "auto-connect" defaults on: members' mail and calendar connect when delegation is set, each member gets a notice and can pause the connection or mark it private, and reads are logged per person. With auto-connect off, the connection activates at the first-run checklist step.
- **Matching**: every message matches a record by address or number; unsure matches go to Needs you ("Needs a match" filter, Undo on each match). One contact record holds every email, phone and handle; likely duplicates are suggested; a merge keeps all history.
- **Views**: By contact (default; one row per person, newest message across email, text, calls), By thread, Calls only. Open a contact as a tab: whole history (collapsed quotes, text bubbles, calls with player, transcript, summary; campaign steps as quiet lines; record chips), header (record link, email, text, call, Follow, Ask), composer that switches Email/Text and picks the sending inbox (replies go out from the inbox the thread came in on), templates, snippets, attachments, Draft (an agent drafts; Send, Edit, Discard, with a Gate line). Every person and company record has a Conversation tab (same thread); email and phone fields show @, bubble, phone icons.
- **Following**: you receive a contact's messages in your Inbox when you own the record, are on its project, follow it, or are on a campaign it is in; also messages to teammates' inboxes about the contact when shared.
- **Sending**: Space sending (campaigns, automations, agents) goes through Resend or Mailgun on the Space's own domain, DNS checks (SPF, DKIM, DMARC) shown green/red. Every agent send passes the Gate.
- **Calls and SMS**: Twilio; one Twilio account per Space; numbers assigned to people, agents or shared inboxes. Softphone dock (Cmd-Shift-K): dial, incoming sheet with the caller's record, mute, hold, transfer to a teammate or agent, record with consent, transcript and summary on the record after, Log a task. Each Space registers its own US texting brand through a guided flow.
- **Recipients**: one recipient field everywhere (tokens, Cc/Bcc, ranked search across contacts, members, inboxes, groups; paste splitting; drag between To/Cc/Bcc; Reply All never includes you or duplicates).
- **Calendar** is a view in Inbox, not a place (Day, Week default, Month; N new event; calendars from Google/Microsoft; availability stripes while adding people; Find a time; drag to create in 15 minute steps). Events link to records, show Join, Ask, Booked by (agent face), From booking page, attendees, Agenda; after the meeting a recording, summary and transcript land in the contact's conversation like a call.
- **Meetings** (Zoom first, then Meet and Teams): a Meeting record (time, attendees, link, recording, transcript); later events update the same record; an Automation step can summarise and pull decisions into linked records with the meeting as source.
- **Permissions**: `comms.shared_send`, `comms.agent_send`, `comms.numbers`, `comms.domains`. Filed mail is visible to whoever can see the linked record.
- **Events**: `message.received`, message.sent*, call.started*, call.ended*, meeting.ended*, message.bounced*.
- **UI**: Inbox place; Console Comms (sending domains, numbers, shared inboxes, texting registration).
- **Inbound mail for non-mailbox addresses**: shared and agent addresses (hello@, support@) are fed by inbound routes via Resend or Mailgun to `/hooks/mail` (MX on the Space domain) into the same pipeline. There is no IMAP hosting. Otherwise the address is an alias to a delegation-connected service mailbox.
- **Contact owner**: Owner is a standard field defaulting to the creator or the campaign owner. Unowned replies go to the campaign owner, then the shared inbox. Only senders with prior outbound contact or in a followed thread raise "Needs a match" in Needs you; others stay in an Unmatched list.
- **Contact preferences and suppression**: a Contact preferences field group holds email consent, SMS consent, Do-not-contact, channel opt-outs, and source and time. One Suppression list is consulted by the single send API for every sender. Inbound STOP and UNSUBSCRIBE are parsed, and bounces and complaints write to the list. Do-not-contact screening blocks adds only; it never removes or deletes a record or a person.
- **Single send API**: campaigns, automations and agents all send through one API that enforces caps, send windows, throttling and suppression. The launch preview shows a sample, counts and exclusions.
- **Message status and deliverability**: ladder queued, sent, delivered, bounced, complained. Events `message.bounced` and `message.complained`. The contact shows a deliverability badge. Message detail shows the provider id, DNS check state and trace id. Hard bounces add to suppression.
- **Call routing and recording**: each number has a route (ring owner, then a list, then voicemail with transcript) and hours. Recording is off by default in all-party consent contexts; an announcement plays and consent is logged. Agent numbers handle texts and voicemail in v1.
- **Alert on replies**: a per-contact Follow option "Alert me on replies" raises that contact's inbound messages to Interrupt within working hours; it is the default for contacts on a campaign you own.
- **Meeting sources in v1**: Zoom, Google Meet and Teams recordings through provider APIs. No meeting bot in v1 (owner to confirm). A meeting without a provider recording is a record without transcript.
- **Private chats and mail**: see 2.15 and 5 (b7) for what the server can read.

### 2.19 Campaign
- **What**: outreach by email and SMS in Apps > Campaigns on the same engine as Automations. Three kinds: one-time send, sequence, triggered (starts when a record event happens such as a new lead or a stage change). Audience from a record view; steps (email, wait, branch on reply/open/click, SMS, task, call task); A/B variants; send windows per recipient time zone; throttling per sending domain; stop on reply; unsubscribe handled; replies land in the Inbox of whoever owns the contact, marked with the campaign.
- **Warmup**: new domains and mailboxes warm up before use (ramp to a warmup pool, health per mailbox: bounce, spam placement, reply; automatic slowdown), built on a fork of Warmbly (Apache-2.0) with our own pool across opted-in Spaces. Cold-email rules lifted in: per-mailbox caps, spacing, stop on reply, suppression.
- **Gate**: campaign launch is a Gate act. `campaigns.launch`. Sending uses the single send API (2.18) so caps, windows and suppression hold for every sender.
- **Events**: campaign.launched*, campaign.replied*, campaign.unsubscribed*.

### 2.20 Site (deployment)
- **What**: anything that runs in a Docker container behind Caddy: sites, apps, APIs, workers, artifacts. Belongs to a person or agent; shareable like anything else; own root folder under Deployments/ in Files; may create its own database that appears as a record type; environment values come from the Vault by key name.
- **Pipeline**: agents build, test, verify and stage; every deployment has a staging URL that is always password protected (a sealed Vault key; shared across a site's previews); only an explicit Promote puts it on production, through the Gate; roll back available. A site with a repo has Previews: one per branch and PR on its own staging address, built on every push, removed when the PR merges (Rebuild brings it back); Promote merges the PR then ships that build, disabled while a check fails or the build runs.
- **Site tables**: site-scoped record types, created by the site's agent or anyone who can edit the site (no schema permission needed), sharing the site's access, listed in Records under a Sites group, promotable to a Space record type by someone with `schema.manage` (Promote checks it); schema changes are versioned migrations with Undo. Forms on a site must target Space record types. Automations may trigger on a site table for anyone with access; Journeys and Campaigns require promotion first.
- **Events**: site.deployed*, site.promoted*, site.rolled_back*.
- **Permissions and domains**: `sites.deploy`, `sites.promote` (a Gate act), `sites.domains`. Site Settings > Domains shows the DNS check and the Caddy certificate state.
- **Site end-user accounts and service identity**: a site can have its own sign-in for outside people (magic link or password, per site, not Space members). Each account links to a record with a row rule. The site runs as a service identity whose grants are capped by its owner's. File links are short-lived and scoped. The API can post into a record's conversation or channel. Stripe connects through its connector. Audit entries name the outside account as actor. See the portal pattern in 3.6.

### 2.21 Kit and Template
- **What**: one package format (manifest, layouts, components, words, behaviours, plus record types, Journeys, Automations, agents, forms, runbooks). It versions with semver on its own channel, previews before it applies, is chosen per Space or per person (Settings), can be rolled back in one click, and is built by asking an agent (Apps) with preview before publish. Behaviour is declarative first with sandboxed scripts that can only call the API (no network, no secrets). Every Kit is tested against a seeded fixture Space before it can publish. Skins become a Kit's theme layer. A Template is a single item saved in the Kit format (an agent, Automation, Journey, record type, runbook, project) and installed from Apps > Templates. Industry Kits (law firm intake, estate planning) install structure in one click.
- **Events**: kit.installed*, kit.updated*, kit.rolled_back*.
- **One extension format**: a Kit is the only installable package. Its contents are typed: ui, structure, steps, tools. A connector is a Kit content type; an MCP server installs as a connector of kind mcp. "Module" is retired. One install sheet lists tools, record types, network domains and vault names. Permissions: `kits.install`, `kits.publish` (admin publish).
- **Tests**: the manifest declares fixtures and expected events and views. Skills ship an eval set (the memory proof set is one). Publish is blocked on failure and the last good version stays live.
- **Sandbox**: scripts and connectors run in a sandbox. Denials (a blocked network call, a denied API) emit `sandbox.denied` events with the trace id, show in the Kit's health and in the Console, and Kits expose a debug panel.

### 2.22 Event
- **What**: every change emits a typed event on one event log per Space. Automations, Journeys, Campaigns, routines, notifications, sync, the audit log and outgoing webhooks subscribe; nothing polls.
- **Fields**: type, actor, on-behalf-of, resource, time, payload (no secret values), cursor (numbered events; clients catch up after any drop; heartbeat every 15 seconds).
- **Contracts**: each capability and event has a contract test.
- **Catalogue**: generated from capability manifests, named `<primitive>.<verb>`. Each event has a version, a schema, an `origin` (actor, run id, trace id) and a `cause`. Events are ordered per Space by cursor and replayable. Automations do not retrigger on events whose origin is themselves unless "allow self-trigger" is on, and a chain depth limit (default 8) stops loops. Events are kept per the retention default (2.26).

### 2.23 Star and Follow
- **What**: **Star** puts anything (chat, record, file, terminal, automation, site, agent) on your Home and in the sidebar Starred section; per person per Space. **Follow** sends you its updates (a followed record's messages reach your Inbox). There is no Pin, favourite or bookmark. Star and Follow are independent toggles. Starring a person or company offers "Also follow", on by default. Inbox visibility uses Follow only. Starred agent faces replace the old pinned faces; "Pinned messages" stay as a content marker in channels; field "pins" become "Keep visible".
- **Events**: star.added*, follow.added*.

### 2.24 Notification
- **What**: three levels, nothing to set up. Interrupt (push and sound; banner top-right with inline actions): only what waits on you with a clock: an approval or review asked of you, a direct message or @mention from a person, an incoming call, your agent blocked on you, an incident you own. Badge (a dot on the place plus a count inside that place's sidebar, no push; the rail itself shows a count only for Needs you and direct conversations): replies on things you follow, tasks given to you, a long agent task finished, campaign replies. Digest (no badge): everything else, gathered in "While you were away" on Home.
- **Rules**: each thing lands where it belongs (actions in Needs you, outside messages in Inbox, conversations in Chats, the rest on Home). The rail shows counts only for Needs you and direct conversations; other places get a quiet dot. One device at a time: while the app is open nothing is pushed elsewhere; after 5 minutes idle on the computer, pushes go to the phone; pushes carry no content ("Northwind needs you"). Working hours respected: outside them only calls, urgent approvals and incidents interrupt. One email backstop after an approval waits 4 hours. Repeated events in a thread collapse; same key collapses to one banner, at most 3 banners; an agent can interrupt a person at most 3 times an hour, the rest go to the digest and the agent is told. Away and delegate: Set Yourself Away asks Until and who gets your approvals (a person, a role, no one); while away only calls interrupt; the delegate's actions are logged as theirs "for you"; I'm Back ends it. Mute on right-click silences a sender for an hour. Settings only adjusts (mute an agent, channel or record, change hours, turn the email backstop off). A Space switcher dot marks another Space that needs you; Interrupt-level notifications from any Space still arrive.
- **Events**: notification.delivered*, away.set*.
- **Delegation**: an away delegate never gains access. Items the delegate cannot act on go to the next delegate or the role, and the delegate sees only the request's blocks.

### 2.25 Audit event, Session, Device
- **What**: append-only record of every change to access and every sensitive act (reveal, send, export, erase, admin change, Engineer MCP call, each admin "everything" view, delegate action). Fields: at, actor, on-behalf-of, action, resource, before/after (never secret values; an erase entry records who and when, never what). "What happened?" opens from every chat turn and Automation run (each step, duration, machine). Session/device: principal, device, last seen, location, revoke.
- **UI**: Console Audit log (filters, CSV export), Console Access > Sessions and devices, Settings > Sign-in and devices.
- **Logs vs audit**: logs hold ids and metadata only, never content, so erasing a person is done by tombstone. Viewing logs is itself `audit.read` or `server.logs`.

### 2.26 Hold and Retention
- **What**: retention defaults per kind of data in the Console (transcripts, run logs, memory, audit entries, trash, backups, records per type, files). A Hold flag on a record, file, channel or person blocks expiry and erasing and shows "On hold" (Place on Hold / Release Hold in its menu). "Erase a person's data" finds everything about one contact across records, files, chats, inbox and memory, shows it, and erases it with an audit entry; erase also purges the next backup rotation.
- **Permissions**: `records.hold`, `policy.manage`.
- **Defaults**: trash 30 days; run logs 90 days; transcripts 1 year; audit 2 years, then archived and never edited; file versions all kept for 30 days, then daily for 90 days, then monthly unless named. All configurable in the Console.
- **Erase vs hold**: erasing something under a Hold needs an owner override with a reason. Erasures write tombstones that are reapplied after any restore, so a backup restore never resurrects erased data.

## 3. Places

The rail: Home, Chats, Inbox, Records, Files; then, in the lower group, Apps, Automations, Vault, Settings. Inbox is a place (topic 15 and a22 text are updated to this list). ### 3.0 The shell (applies to every place)
- **Layout**: rail (places), a place sidebar, a main view with tabs, a right pane with its own tab strip. Anything opens beside the main view as a side tab (file, thread, chat, channel, agent, record, event, diff, terminal). Main-view tabs: the "+" after the last tab (or Cmd-T) opens a new tab with one search ("Open anything, or start something": Start, Chat with, Recent, Record types, Folders; the same `@`, `#`, `/` prefixes as Cmd-K). Enter fills the tab, Cmd-Enter opens a new tab. Opens in-tab with a shared component: tasks, projects, hires and Journey records (plan), chats, threads, files, agent and person chats, runs. Opens in its own place (the tab shows an "Opened in" card with Open again): channels, contacts, companies and other records, folders, automations, record types.
- **Cmd-K search** (single, permission-filtered, snippets with source links): reaches People, Agents, Chats, Inbox, Records, Files, Automations, Apps, Settings. Recent before typing. Prefixes: `@` people and agents, `#` chats and records, `/` files, `>` actions (New task, Call Elena, Switch skin, Set yourself away, Go offline). Results merge server hits (shared content) with local-replica hits (private chats); the phone searches what its replica holds and says so. Enter opens through the place; Cmd-Enter new tab; right-click Open, Open in New Tab, Copy Link. Switch skin previews each skin as you arrow through; Esc restores yours. Type filters.
- **Title bar**: Space name, skin dropdown (13 skins plus System, seven dark and six light; instant; personal per Space), tiny confirmations, "Offline, N changes waiting", "Away", Saved.
- **Offline**: edits queue on this computer and send in order; click opens Waiting and Conflicts (section 4.14).
- **Empty/Offline/Error**: every place uses one component: one line, one primary action ("No results", "Couldn't load Records", Try again / New record). A new person's first Home is a setup checklist.
- **Keyboard**: Cmd-K search, Cmd-T new tab, Cmd-1..9 jump to starred agents (Chats), Shift-Cmd-1..3 switch Space, Cmd-D star, Cmd-Shift-K softphone, Cmd-F finds any Settings row, ⌥↓ Next unread.
- **Two symbol tables, documented in Settings > Keyboard**: Composer: `@` people and agents; `#` things, grouped Folders, Channels, Records, Files and narrowed by typing (a folder becomes a chip); `/` commands, skills and templates. Cmd-K and the new-tab search: `@` people and agents; `#` chats and records; `/` files; `>` actions; plus type filters.
- **Tabs** are per device and per Space and are not synced; Starred is synced. Switching Space restores that Space's tabs (2.1).
- **Arrow-out marks**: on a project or Journey record the Files and Chat tabs carry a small arrow-out mark because they open in another place. Hover shows where ("Opens in Files", "Opens in Chats"); Cmd-click opens the item as a tab in that place; plain click navigates there. Templates are not a separate list: "New project" and "New <Journey type>" open a picker of templates to start from (an empty one first).
- **Comment threads** end in a full-width reply field with an up-arrow send button at the right edge. Every pane has exactly one toggle, at the far left of its header; an inner toggle hides while the side panel is open.
- **Report a problem** is the last item of every right-click menu, added by the shared menu component (modules never add it by hand), and is also in the Help menu and on Cmd-Shift-/ (section 5, Report a problem).
- **Space switch**: see 2.1. Each place shows a skeleton while the Space loads and never mixed data.

### 3.1 Home
- **Purpose**: your day across the Space.
- **Layout (top to bottom)**: Needs you (top 3), My work (the full list; assign from a face; "Assigned by you"), Projects at risk, While you were away, today's routines, Today (your calendar day), Starred, Quick start / first-run checklist, the Ask box.
- **Rules**: Projects at risk = overdue, blocked or slipped; the section menu shows the counting rule. While you were away (Provisional, b2): a ranked digest written by your assistant: three lines on top, then at most seven items: decisions agents made for you (each with Undo), work finished on your projects, changes on records you follow, routine results (one line per routine), anything waiting on you that is not urgent; it resets once seen; "See all" opens the full activity for the period. Starred includes terminals with live status (running or exited, last line); one click reattaches.

### 3.2 Chats
- **Purpose**: conversation with agents and teammates.
- **Layout**: sidebar top to bottom: your avatar and Space name (switch Spaces; red dot when another Space needs you); search and new-chat icon (your assistant, no label; @ brings anyone in); Needs you (only when something waits; approve or send back from the sidebar); Starred agent faces (a click returns to the last chat, "+" starts a new one, Cmd-1..9 jump; All agents picks who is starred); Recent (Starred, Today, Yesterday, Earlier; a pulse where an agent is working; filters All, Unread, People, Agents; Next unread); Channels sit above Recent, as in the prototype (ruling 45). Middle: the conversation. Right pane belongs to whoever you talk to: Computer, Threads, Files, Memory, Routines as quiet tabs. Agent work folds into "Worked for 14s, 3 steps". Helpers live under the chat that started them.
- **Agent page** (from its name in a chat header): photo, name, role, Chat button; tabs Chats, Memory, Files, Computer, Settings; "Automation runs" button beside Chats.
- **Flows**:
  1. Start a chat: new-chat icon, an agent's face, or New channel. The chat starts on your preferred provider and model; the model switcher changes provider and model at any point and lists only what you have connected or can reach through the vault. Fallback order in Settings is the chat default.
  2. Ask an agent: type; your Vyre fetches the agent's files; the turn runs on your computer with your account and IP (phone or computer off: on the Space); transcript, results and new memory save to the Space as they happen so a teammate opening the chat sees it live.
  3. Address an agent in a channel: @mention > it posts one line in the main conversation that opens its thread ("Intake is on it") > it works inside the thread (streaming, thinking, tool calls, files, computer) > it posts back to the main conversation only for a result, a question someone must answer, or when asked; results quote into the main conversation with a link.
  4. Steer a working agent: reply in its thread; a message while it works queues for its next step; Interrupt sends it now. Per-agent Stop and Stop all in the conversation header. Handing work to another agent opens that agent's thread linked from its own; exchanges are limited to 4 hops before a person must reply.
  5. Switch an agent's mode: click its face in the thread header: Leads/Listening, model and provider, effort, whose account pays, Ask to review, Remove; L toggles lead; "+" adds an agent as listening. The composer line says who will answer ("Intake will reply" or "No agent will reply, type @ to ask one").
  6. Switch engine mid-chat: see 4.6.
  7. Needs you: a two-column inbox (rows left; selected request right with what, why, source, one primary action and Send back); one list sorted by urgency (blocked and due first) with a quiet filter menu; no groups.
  8. Make a private chat into a channel: @mention a person > "Start a channel with them".
  9. Connect an outside agent: channel menu > Connect an outside agent: MCP address, one-time token (once, 10 minutes, reveal/copy logged), run command, permissions (read, post in threads, read changesets on; changing files on a branch off and needs approval; Vault values never available).
  10. Agents open and switch side tabs for you (off in the tab menu; a line says so).
- **Plans** are documents agents write: edit any paragraph, select text to comment or ask the agent; suggestions arrive as tracked changes.
- **Message hover bar**: Copy and Edit stay in the hover bar and right-click.
- **Helper chats**: a helper's chat opens in the same pane with an address bar at the top ("Research > Firms 1-3"; each part links back). A helper chat is read-only: no composer, because helpers take no messages (a note says so; steering goes through the parent thread). While helpers run, a Helpers icon appears in the chat header beside search, sidebar toggle and menu; it lists running helpers with status and opens one on click.
- **Turn errors** reuse the shared error shape (4.18). The chat shows an inline row (what, why, next: switch model, use backup key, ask for access) and Copy trace id. "What happened?" lists steps, durations, machine, model, key used and denials. The model switcher greys providers that are disallowed for the open labels.
- **Your assistant's scope**: it can create a personal or team Automation for you, edit, summarise or troubleshoot one you can, operate in records and files, create agents and folders and share them for you, and add Vault items with the right structure. For a Vault item you paste the secret directly into the value field; the assistant never sees it.

When something slips the plan proposes the cascade ("3 later tasks move, the Tuesday consult still holds") with Apply or Keep dates; an agent can propose the same.   5. GitHub: Pull requests and Issues are two synced types from vyre-ai/website; PR page tabs Overview, Changes (opens the diff as a Files tab), Preview (opens Apps > Sites > Previews); a failing check shows "Ask <author agent> to fix" (makes a task); "Assign to agent" on an issue makes a task and the agent's result lands as a linked changeset.

- **Record page right pane**: the first tab is Activity, open by default and closable; any linked record, file or thread opens beside it as a tab. Status shows once, under the name, as a dropdown (not repeated in the fields). Assigned shows under the name too and is a person picker.

### 3.6 Apps
- **Purpose**: things you publish or send out. Sections: Sites (deployments), Forms, Campaigns, Templates (gallery of template packages); Kits are built here by asking an agent (choosing a Kit is in Settings).
- **Layout**: three-section sidebar (Sites, Forms, Campaigns), each engine renders its main view and detail pane; Campaigns adds sending domains, mailboxes and warmup.
- **Flows**:
  1. Publish a form: Forms > New > pick a record type > fields (Ask/Show/Hide, prefill keys, signed links) > design > consent/captcha > publish link or embed in a site. Submission writes a record, fires `form.submitted*`, and sets First/Latest source.
  2. Create a booking page: calendar, length, buffer, questions > a booking creates/updates a record and a meeting.
  3. Launch a campaign: pick kind > audience (a record view) > steps > send windows/throttle > preview > Launch (Gate approval) > runs; replies land in the owner's Inbox; Stop on reply.
  4. Deploy a site: the site's agent builds, creates tables, reads env values by Vault key name, deploys to the password-protected staging URL, then Promote (Gate) puts it live; Roll back.
  5. Install a template: Templates gallery > preview what it adds > install.
- **Email builder** (one component for Campaigns, Inbox templates and Automation email steps): block editor (text, image, button, columns, divider, merge fields, HTML block), full HTML mode where an agent can write the HTML and place it, plain-text version, focus mode (Cmd-Shift-F) that hides everything but the email, preview as desktop, mobile and dark, preview as a record, send test. An Ask Vyre pane with an agent selector edits or drafts the email ("make it warmer", "write the HTML"); its changes appear as a diff accepted per change. Autosaves as versions.
- **Site editor modes**: the top switcher has Build, Code and Preview. Code shows the site's files in an editor with Find and diff; Ask Vyre (agent selector) edits the code, builds it and iterates with you. Every change is a version and a changeset the agent can propose; staging updates on save, production only through Promote.
- **Client portal (b18, owner direction)**: there is no native portal. A portal is something a coding agent builds and deploys as a site, and the API makes that easy and safe. v1 includes: site end-user accounts (magic link or password, per site, not Space members); each outside account linked to a record (a contact or client) with a row rule so it sees only records related to it; a site service identity whose grants never exceed what the site's owner gave it; short-lived scoped file links; posting into a record's conversation or channel through the API (it lands in the Inbox like any message); payments through the Stripe connector; and every portal action audited with the outside account as actor. A portal template in the Templates gallery shows the pattern.
- **E-signature (b19, owner direction)**: one Signature step and one Signature task kind, with three providers behind the same interface. Documenso is the default, run unmodified as its own container on the Space server (no account, no per-envelope cost; its AGPL licence is fine because Vyre never forks or links it and only calls its API; this is the one container exception to the b12 libraries rule). Dropbox Sign and DocuSign are connectors for teams that already use them. The step sends a file from the record's folder with signer fields mapped from the record, tracks Sent, Viewed, Signed and Declined as events (`signature.sent`, `signature.viewed`, `signature.signed`, `signature.declined`), posts its run thread in the record's channel, and saves the signed PDF and audit certificate as a new version in the record's folder. Sending goes through the Gate. Switching provider never changes an Automation.

### 3.10 Console (separate site)
- **Access**: console.<space-address>, Vyre login, Owners, Admins and Developers (`console.access`). Team Spaces only; a Personal Space has no console. Runs on the Space's own server so it can troubleshoot that server. Not linked from the app.
- **Top bar**: Space mark and name, "Console", health dot, Cmd-K, Assistant toggle (Cmd-J), skin, Open the app, the admin.
- **Navigation (CONSOLE-SPEC, binding)**: Overview (health, attention, recent admin activity, usage); Access (People, Groups, Roles, Grants, Policies, Access checker, Access reviews, Sessions and devices); Agents and actors (Agents register, Outside actors, Agent computers, Agent template); Data (Schema, Sensitivity labels, Retention, Holds, Erase a person, Backups, Export); AI (Models and providers, Gate rules, Spend and limits, Logging, Review sampling, Incidents, AI use policy); Comms (Sending domains, Numbers, Shared inboxes, Texting registration); Integrations (Connectors, Connections, Webhooks, API keys); Infrastructure (Network: domain, certificate, relay, servers; Server: updates with roll back, live logs, diagnostics, services, support bundle); Audit log; Space (identity, legal name, logo, defaults, danger zone). - **Console assistant** (right pane, Cmd-J): your assistant with the Engineer MCP for Owners, Admins and Developers; sees the current page; proposes changes as a diff card with Apply; every change audited "on behalf of". It explains access ("why can Omar see Rivera?"), drafts a custom role, builds a record type, fixes a failing diagnostic, connects another server. - **Governance**: Data: retention, legal hold, erase a person's data, labels with rules (Restricted is never sent to an AI provider or mirrored to a laptop; Confidential only to approved providers), sensitive-data detection suggesting sealing, data location, sharing rules, quarterly access reviews with one-click removal. AI: allowed models per label, agent register, Gate defaults and per-agent overrides, spend caps (agent, person, Space) and pause-all, logging, memory rules, "Drafted by an agent" label, review sampling, AI incident log, outside actors and Engineer MCP access, AI use policy export; Allowed AI accounts (Any, or Company only).

- **Binding list**: CONSOLE-SPEC is the binding navigation. The shorter twelve-page list from the brainstorm is a pointer only. Pages hide by permission (a Developer sees Schema, Integrations, Infrastructure logs and no people management).
- **Server down and versions**: `vyre-server doctor` and the support bundle run from the shell and from the relay's status row, so a down server still has a way in. The server supports apps within 2 minor versions; older apps show "update required" and go read-only.
- **Reset password and removal**: the reset confirm lists the full loss: Mine vault items, private chats and personal memory all use the same key, so all are lost unless a recovery code was saved (offered at sign-up). Removing a person rotates the Space data key epoch and the server stops serving them at once; their devices purge on the next contact. Restricted data is never on laptops (the mitigation); data already on a malicious device cannot be recalled.
- **Sign-in policy page**: second-factor floor and SSO providers.

## 4. Cross-cutting rules

### 4.1 Star and Follow
Star = on Home and in Starred; Follow = receive updates; independent toggles (2.23). Star menu on any chat, record, file, terminal, automation, site, agent. Starred agent faces replace Pin. Following a person or company record routes their messages to your Inbox (2.18).

### 4.2 My work and the work queue
One queue: approvals, reviews (changesets, campaign launches, memory promotions), questions from agents, assigned tasks, Journey tasks and issues assigned to you are all tasks. Home My work is the full list; Needs you (Chats sidebar and phone) is the same list filtered by the rule in 2.8. No separate Tasks place.

### 4.3 Run
All long-lived or repeatable work is a Run (2.13). Failed runs go to the owner's Needs you. Single Runs view in the Console.

### 4.4 Gate
One approval model (2.14). Arrives as a task. Previews are exact. Agent send, campaign launch, deployment promote, push to a protected branch, secret export and delete go through it.

### 4.5 History
One pattern for files, records, Automations, memory, Kits and agent definitions: versions with who and why, compare as a diff tab, restore. "Undo this run" groups every write of an agent run under a run id on the run chat. Undo reverts only writes whose current version is still the run's and reports the rest; sent messages and deployments are listed as not undoable.

### 4.6 Composer
Chats, threads, Ask panes, inbox email and text, record comments and task threads share one composer: `/`, `#`, `@`, attachments, recipients where it sends outside, and the "who will answer" line. The symbol tables are in 3.0. `[[` links a record. Switching engine mid-chat: every turn of every engine (API and CLI, via hooks) is written to one canonical transcript; a rolling summary is kept fresh in the background; the new engine starts with the summary, the last turns verbatim (default last 20 turns or about 12k tokens, whichever is smaller), a pointer to `chats/<id>/transcript.md` and an instruction to search or read it; tools `transcript_search(query, mode)` (keyword, semantic or hybrid default), `transcript_read`, `transcript_get(turn)`. SQLite FTS (BM25) updates in the write; embeddings (sqlite-vec, small local model) a moment later; hybrid fuses with recency. A quiet line records the switch ("Switched to Codex, picked up from the summary and the last 20 turns"). Long chats compact to summary plus retrieval. CLI engines (Claude Code, Codex, Grok, Gemini CLI) run on your subscriptions; API models (OpenRouter, Anthropic, OpenAI, OpenCode Go, local) run on our own engine (tool loop, streaming, retries, cancel, compaction, subagents, Ask/Allow/Auto), with the Vercel AI SDK as the adapter layer only.

### 4.7 Tabs
Main tabs and side tabs (3.0). Closing keeps the state of diffs and viewers; a diff tab is a tab like any file.

### 4.8 Ask
A lightweight thread with an agent about what you are looking at (a record, file, event, page). The suggested agent is who booked the event or the contact's agent. Agent leads in an Ask thread. Ask is a private chat scoped to the object (2.5).

### 4.9 Folders and sharing
One pattern everywhere (2.4). Share sheet: person, group, role or agent at View, Use, Edit or Manage. Public/guest sharing is governed by Console sharing rules and `files.share_external`.

### 4.10 Notifications
2.24.

### 4.11 Offline and conflicts
Local-first: a partial encrypted replica of what that person may access, filtered per person on the server. Revocation and leaving purge the local copy (with a test). Offline: "Offline, 3 changes waiting"; edits queue and send in order. When two edits collide (records, files, memory) your assistant diffs both sides, picks or merges per field, shows a short summary of what it chose, and pushes once the summary exists; every choice has Undo (Redo restores). A Conflicts tab (sync status; Needs you only when the assistant is unsure) lists every resolution. Files keep both versions. Merge model (b6): structured fields merge per field with a logical clock (newest wins, loser kept in history); long text (notes, docs, AGENT.md) uses a CRDT; files keep every version. What is a conflict: concurrent edits to the same field from different bases with different values. Plain fields: newest wins, loser in history. Status, money, owner, locked-after-approval and sealed fields always go to the assistant for a proposal and to Needs you for confirmation. An edit rejected by a revoked permission or a lock goes to a "Rejected" list the person can copy out. The assistant never sends Restricted fields to a provider; those conflicts are a plain two-value choice. Assistant resolutions cover only fields the person can edit.

### 4.12 Permission evaluation
One decision, explainable (Access checker shows each step in words). Can principal P do action A on resource R?
1. P's roles (union over P and its groups' roles) include the permission for A.
2. A grant exists on R or an ancestor to P, a group or a role, at a level that includes A, whose conditions match (row filter, hidden fields, expiry, time).
3. R's label is within P's clearance (highest clearance among P's roles).
4. Policies last: Gate (needs approval), limits (spend), label rules (which provider, laptop sync). Label vs provider is checked at tool-result time: an agent or outside actor on a disallowed provider that asks for a Restricted or Confidential record gets "Restricted: not available to <provider>; switch to <allowed provider> or use a local model", and the attempt is logged.
5. An agent acting for a person gets the intersection of its access and that person's; a scheduled or routine run acts with the agent's access intersected with its owner's (a routine: its setter's). No agent gains access through a person it is not acting for.
6. Owners of a resource always have Manage on it unless a hold or a label above their clearance blocks it.
No explicit deny grants; deny wins only through clearance and holds. Principals: people, agents, outside actors, services. Built-in roles: Owner (all), Admin (all but transfer ownership and delete Space), Developer (console access, Engineer MCP, schema, connectors, logs, no people management), Member (everyday verbs), Guest (view and comment within explicit grants only). A "View as" control previews what a member sees.
Catalogue (rows of the matrix; keys; additions from the gap rulings are marked +): Space: members.invite, members.remove, access.manage, policy.manage, audit.read, console.access, engineer.mcp. Records: records.create, records.edit, records.delete, records.export, schema.manage, records.reveal, records.hold. Files: files.write, files.delete, files.share_external. Chats and channels: channels.create, channels.agents, chats.private. Agents: agents.create, agents.manage, agents.schedule, computers.use. Automations: automations.personal, automations.space, campaigns.launch, journeys.manage. Comms: comms.shared_send, comms.agent_send, comms.numbers, comms.domains. Vault: vault.shared_create, vault.reveal, vault.export (high risk), vault.policy. AI: ai.models, ai.spend, ai.incidents. Server: server.update, server.logs, server.services, server.backups, server.network. Each has a risk dot (low, medium, high). Added rows: Apps `forms.publish`; Sites `sites.deploy`, `sites.promote` (Gate), `sites.domains`; Kits `kits.install`, `kits.publish`; Runs `runs.manage`; Terminals `terminal.use`; Records `records.share_external`; Journeys `journeys.manage` (already listed); Agent computers `computers.use` split into watch and take over. Each new row carries a risk dot and default roles (Admin and Owner on; sites and kits publish default off for Member).

### 4.13 Agents lead and listen
2.5. A message in a Leading thread is answered by the lead; Listening agents answer only when @mentioned or asked ("Ask Docs to review this"). Hop limit between agents; each agent's work in its own thread.

### 4.14 Own inference
Every turn runs on the asker's own account by default, so the same agent can get a different model or limits from one teammate to the next. A team wanting uniform behaviour shares an API key through the vault; the agent's model setting points at it ("use #Team_Anthropic_Key"), usage logged per actor. No "Space account" concept. Subscription sign-ins (Claude Code, Codex) stay per person, marked Mine, follow you across Spaces and devices. A subscription session is stored in the person's Mine vault and used by server runs only for turns that person started or for a routine or personal automation they own, under a standing switch "Let the Space run work on my subscription" (default on). CLI logins run in a per-person server sandbox; revoking the switch kills the sandbox. Tasks use the key chosen on the step plus a backup. A wake-up that finds the starter's token expired posts an Unblock and falls back to the backup key (2.13). A turn in a thread, including background wake-ups, runs on the account of the person who started the thread; anyone who steers it pays for the turns their message causes. Governance can restrict accounts to Company only.

2.15.

### 4.16 Kits
2.21. A design change is a Kit update and never needs an app release.

### 4.17 Security modes
Sensible defaults; each person picks relaxed, standard or strict; the owner sets a floor nobody goes below. Ask, Allow and Auto modes per Space and per device, for terminal use, Chrome use or both (Personal Space terminal included). In Auto nothing prompts; the work-folder lock is a hard wall; the always-ask list stays; the "in use" indicator and Pause stay; every command and click is logged under the agent with your name. Team agents may use your laptop's terminal only if you opt in per Space, locked to a work folder inside that Space's sealed folder, with a visible indicator; a chat on your laptop runs the engine headlessly with Vyre's tools only (no laptop terminal or disk by default).

### 4.18 Errors, health and diagnostics
- **Error shape**: every capability returns `{code, message, cause, next, retryable, traceId}`. Codes group into auth, rate limit, validation, provider, timeout, permission. The run chat shows it on the failed step with Retry step, Edit, Replay and Copy trace id; the owner's Needs you card carries the same. Agent turn errors use it too (3.2).
- **Health checks**: each manifest declares a cheap, idempotent health check with states Healthy, Degraded and Down and a last-checked time. The Console Overview and each connection's header show them. An unhealthy dependency pauses its automations with a visible reason.
- **Trace id**: created on the device when an action is queued, kept through the outbox, and sent as a header or metadata to providers where supported (message headers, API metadata); outgoing webhooks carry it.
- **Logs**: structured, ids and metadata only (no content), with fields when, trace id, who and for whom, capability, record, result, duration, cost, `label`, `space`, `device`, and app and server version. Erase works by tombstone.
- **Client log**: the app writes a local ring-buffer log keyed by trace id, included in the support bundle and uploaded on reconnect.

## 5. Platform (b5 to b14 and neighbours)

- **b5 Where data lives**: the Space server holds the truth; each device keeps an encrypted partial replica of what that person may access, opens instantly, works offline, syncs both ways. A Personal Space lives only on the device with an optional encrypted backup.
- **b6 How edits merge**: per-field logical clock for structured fields (newest wins, loser kept in history); CRDT for long text; files keep every version; the assistant steps in only when two meaningful edits genuinely conflict.
- **b7 What the server can read** (two guarantees). (a) Private from other people, admins included: private chats, personal memory and Mine vault items are encrypted under the person's key. The server runtime can decrypt them only while running that person's turn, using a key the person's device wrapped for the Space runtime (opt-in "Let the Space continue my chats when my computer is off", on by default as decided in b8, revocable). (b) Sealed fields and Shared vault items are encrypted under the Space key and decryptable only by the vault service at fill time; never indexed, never logged. Everything else shared in the Space is encrypted at rest with the Space key and readable by the server, so search, agents and automations work. Server-run agents read only what their access allows. Transcript search by others covers channels, threads and shared chats only.
- **b8 Where agent work runs**: private chats you start with an agent run on your device with your account; group chats and channels (more than one person), scheduled runs, routines, automations, Journeys, campaigns, background waits and agent computers run on the Space server; every turn uses the account of the person whose message started it; if your device goes offline your private chat continues on the server with your account, under the opt-in in b7.
- **b9 One API for everything**: one typed, versioned capabilities API is the only way to change anything; screens, Kits, agents (as MCP tools), outside actors, connectors and automations call it; one permission check and audit; whatever a person can do in the UI an agent with the same access can do through the API. One Vyre MCP with toolsets: records (describe schema, query, create/update, bulk upsert with idempotency keys, history and "as of" reads, relations, file fields, webhooks, subscribe), files and memory, vault handles, Automations and Journeys, chats and channels; the Engineer toolset (schema changes, connectors, settings, server troubleshooting) only for agents whose person is an admin/developer. Outside agents change data only by default; additions go straight through, destructive schema changes show a diff; all logged under the agent with the person's name. Every call respects field and record permissions.
- **Built to extend and to fix fast (binding architecture principle, topic 17)**:
  - *Extending is adding, never editing the core.* Everything new plugs into a named extension point: record types, fields and views; Automation steps and triggers; connectors; agent tools and skills; Kit screens; Apps kinds. The manifest also covers field types, views, Gate act kinds, task kinds, block types (the native blocks agents send), import sources and notification kinds; an unknown kind renders as a generic block with the trace id. Each is a versioned package declared in one manifest with typed inputs and outputs, so the API client, the agent (MCP) tool, the docs and the tests come from the same declaration.
  - *One trace for everything.* Every request, run, agent turn, sync and event carries one trace id from the screen to the server and back. Every error in the app shows what failed, why, what to do next, and a Copy trace id; the Console finds everything for that id in one view.
  - *Clear logs.* One structured format: when, trace id, who acted and for whom, which capability, which record, result, duration, cost. Never secret values. Searchable in the Console by person, agent, place, record, run or trace.
  - *Diagnose in one click.* "Report a problem" bundles the trace, recent events, versions and a screenshot into a support bundle (next bullet). Each manifest has a health check (4.18); the server has a doctor; the Engineer MCP (the topic text says "Engineer agent", retired, Appendix A) can read traces and logs and propose the fix as a changeset. Fixes target only Space-owned objects (connectors, Kits, automations, agent files, schema) as changesets approved by the object's Manage holders. A product bug produces a support bundle, not a changeset.
  - *Report a problem.* Last item of every right-click menu (added automatically by the shared menu component), also in the Help menu and on Cmd-Shift-/. It captures what was right-clicked (place, item id, hash), the trace ids of the last 20 actions, recent events and errors, app and server versions, device, a screenshot of the window and the local ring-buffer log. Secrets are never captured; Restricted and sealed values are redacted by label. The sheet has one optional line "What went wrong?", an expandable preview of exactly what is sent, and Send. Destinations: (1) the Space's admins get a task in Needs you (kind Review, "Problem report from Omar"); (2) the Vyre team gets it when the Space policy "Send problem reports to the Vyre team" is On (default On; an admin can set Ask or Off): a POST to reports.vyre.run (beside relay.vyre.run) stores the redacted bundle, opens a GitHub issue in vyre-ai/vyre labelled bug with the trace id, versions and steps (screenshot attached), and files a record in the Vyre team's own Space (Reports type) where an Engineer agent triages it (duplicate check, likely cause from the trace, proposed fix). This replaces sending only with explicit consent. Offline reports queue in the outbox and send on reconnect. The reporter sees "Sent, #1234" and gets a reply in their Inbox when it is fixed. The bundle contents are listed and previewable before sending.
- *Replay.* Because every change is an event, a failed run or a sync conflict can be replayed against a copy of the Space. Replay runs in a sandbox with outward capabilities stubbed (sends and deploys are recorded, never executed), sealed and Restricted values replaced by synthetic ones unless the replayer holds clearance, and needs `server.logs` plus `console.access`.
  - *Tested by default.* Contract tests for every capability and event; the golden flows (lead to client to project, a person joining, agent changes reviewed and pushed, an offline edit and conflict, lead to campaign to reply to call, site deploy and rollback, Gate approval and expiry, memory promotion, offboarding, key failure fallback, backup restore with tombstones) run end to end on a seeded Space before every release, each asserting its events and one trace id; every Kit, connector and step is tested against that Space before it can publish.
- **b10 Events**: 2.22.
- **b11 One index**: one index per Space server (full text plus vectors) covers records, files, chats, inbox, memory, transcripts with permission filtering at query time; end-to-end content (private chats, personal memory, Mine items) is not in the server index; each device indexes its own replica for offline search; Cmd-K, agent tools and memory read it.
- **b12 Technology base**: TypeScript end to end; UI in one codebase (Expo/React Native for web, Mac, Windows, phones) rendered by the Kit runtime; server as one installable service on Linux or Mac with SQLite per Space, Caddy in front, Docker for Deployments and agent computers; reuse the 0.6 kernel, vault, relay and Chrome extension code where it works. MIT/Apache libraries only (notice file; AGPL/GPL blocked by a build check). Avatars: DiceBear Notionists (agents), Boring Avatars (people fallback), Minidenticons (outside). Graph: sigma.js and graphology. Mail: imapflow, mailparser, nodemailer, Gmail and Graph APIs, mailauth for deliverability checks; Twilio Voice JS SDK; Warmbly fork for warmup.
- **b13 Releases**: four independent channels: the app (rare), the server (auto-updates with backup and roll back), Kits and connectors (per Space, versioned, previewed, instant).
- **b14 How we know it works**: contract tests for every capability and event; every Kit tested against a seeded fixture Space before publish; the 50-question memory proof set; a real-install walkthrough of a fresh Space before every release.
- **b15 Several Spaces on one person**: own keys, data, profile and Kit each; the switcher shows a dot for Spaces that need you; Interrupt-level notifications from any Space still reach you; the rest wait.
- **b1 Kits**: 2.21.
- **Networking**: a Space has one address (own domain with automatic HTTPS, or an outbound tunnel via the relay). The relay is its own self-hostable repo; vyre.run is a convenience; nothing depends on us; invite links pin the Space key so a relay only sees ciphertext for app traffic. Public hostnames (forms, sites, booking pages, `/hooks/<source>`) cannot pin a key, so the relay runs as SNI/TCP passthrough for them: the certificate is issued on the Space (DNS-01 or HTTP-01 via the relay) and Caddy terminates TLS. Public hostnames and `/hooks` are listed in Network. A Space without public ingress shows "Forms and webhooks need a public address". Live connection: heartbeat every 15 seconds, numbered events, catch-up after any drop; offline servers as grey rows with Reconnect and Remove.
- **Backups and export**: encrypted, to S3 or a drive, one switch; restore from the Console; owner one-click full export.
- **Mounted folders**: see 2.16; Google and Microsoft built in via DWD/app registration.
- **Governance defaults taken (audit list)**: Cost controls (Space monthly caps, pause-all, agent.toml cannot exceed; Needs you card "Intake hit its daily limit: Raise once or Stop"); Kits (which include connectors and MCP servers) and outside agents need an install sheet (tools, record types, network domains, vault names), admin-only publish, one-click token revoke; sign-in with TOTP/passkey and an owner floor; consent/captcha/rate limits for public forms and consent-aware tracking.

## Speed and smoothness (binding)

Speed budgets (binding, tested on the seeded Space on a mid laptop and a mid phone; a packet is not done if it misses its budget):
- Open the app to usable: under 1 s desktop, 1.5 s phone (reads from the local copy, never waits on the network).
- Switch tab, open a record, file, chat or place: first paint under 50 ms, complete under 100 ms.
- Cmd-K and search: local results under 50 ms; server results merged in under 300 ms.
- Start a new chat: ready to type under 100 ms. Resume any chat: last 50 messages under 100 ms, older ones stream in.
- Send a message: shows instantly (under 16 ms, before the server answers). First streamed token: the provider's own latency plus under 150 ms of ours; streaming renders smoothly at 60 frames per second.
- Scrolling: 60 frames per second through 10,000 rows, messages or files (virtual lists everywhere).
- Switch Space: under 500 ms with a skeleton, never mixed data.
- A local edit: under 10 ms; seen on another device under 500 ms.
How: everything reads from the local copy; agent engines kept warm (a resumed chat never cold-starts its engine); one persistent streaming connection per device; hover and keyboard focus prefetch; code split per place; no layout shift; every span timed in the trace so the console shows where time went; speed tests run in the fast checks and fail the packet.


## Vyre is the agent's native environment (binding)

native environment (your rule)
- Every feature a person has is a native tool for agents. The agent toolset is generated from the same capability manifests as the API, so nothing is missing or added later: terminal sessions, its computer and Chrome (Vyre for Chrome), choosing model, provider and effort for a sub-task, changesets and diffs, interactive questions, plan mode, opening tabs for you, Sites (build, tables, deploy, preview, promote through the Gate), Files (navigate, read, write, mount Google Drive, SharePoint, OneDrive and GitHub, git and versions), Records, Inbox and Calendar, Automations and Journeys, tasks, memory and the Vault.
- Always with the asker's access. Each tool call runs as the intersection of the agent's and the asker's access, through the same permission check, Gate and audit as the UI.
- Rendered natively in chat. Tool results appear as the app's own blocks, never raw text: a terminal block you can open as a tab and star, a changeset card that opens the diff tab, a question card with options (single, multi, free text) that waits for your answer, a plan card with steps you approve, edit or reject before work starts (plan mode), a "Opened client-intake.pdf beside the chat" line when it opens a tab for you, a deploy card with status and preview link, a mount card, a record card.
- Plan mode is a per-thread switch: the agent may read and plan but changes nothing until you approve the plan; approved steps then run and tick off in the plan card.
- Memory and Vault, the right way. A built-in skill every agent carries ("Working in Vyre") teaches it: save facts to the asker's layer, propose promotions, cite sources, search memory before asking; use secrets only by name through the Vault (fill, inject into a terminal or deployment, never print or store values), request missing keys with a Vault request; never copy data across Spaces.
- Outside agents get the same toolset over MCP, so Claude Code or Codex connected to a Space behaves the same way.
