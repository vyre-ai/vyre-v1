# Lead rulings (export from the tracker)

- 1 | Sync protocol and device-store changes from the sync spike | Adopted in ARCHITECTURE-V1 5.3/5.4/5.10: seen_rows per device; Op.after link; bulk multi-row apply with hide-seq guard; web/desktop replica engine sqlite-wasm-cipher 2.2.4 (FTS5, at-rest encryption proven in Node), wa-sqlite 1.0.0 fallback; real-browser OPFS check pending.
- 2 | No @ts-nocheck in v1 | Lead ruling: no file in vyre-v1 may carry @ts-nocheck; ported 0.6 code gets real types when it is ported; reviews reject it; P-PR_58 lint should fail on it.
- 3 | P-PR_47 device items | Ruling 3: the real-phone sideload and Gradle items move to P-PR_47b, which does not gate G0. Item 3 (web encrypted OPFS in a real browser, headless Chrome on a runner) and the S6 numbers in item 5 must still be done in P-PR_47, with s6.reactive under the 20 s cap.
- 4 | Mac and Windows desktop builds | Ruling 4: the Tauri desktop shell builds on GitHub-hosted macos-latest and windows-latest runners (desktop jobs only, release and the spike); everything else stays on our Linux runners.
- 5 | Web replica writes | Ruling 5: on web the encrypted OPFS store costs about 28 ms per commit, so the device store batches local writes (one transaction per frame, about 16 ms) while the UI updates optimistically from memory; the local-edit budget (under 10 ms) is measured to the in-memory apply, persistence follows in the batch. Open via sqlite3mc_vfs_create wrapper.
- 6 | Orphaned packets | Ruling 6: a packet stuck in_progress with no live worker for 15 minutes is reset to ready by the lead with a comment; the feeder re-dispatches it on its branch.
- 7 | changelog.md | Ruling 7: packets never edit changelog.md (shared file, would collide). The lead generates changelog.md from approved packet titles and merged PRs at each integration point and at release (one PR), so the changelog rule is met without conflicts.
- 8 | Agent tool surface | Ruling 8: every capability an agent may use is a tool (agent-native rule), but only the frozen default set (about 60 tools, P-PR_37) is loaded into every turn. All others are reachable through a built-in tool search and load on demand (the same pattern as deferred tools), scoped to the asker's access. Manifests keep agentTool on every eligible capability; the default list is a separate frozen file. No capability is dropped.
- 9 | Contract frozen | Ruling 9: the contract (1,486 capabilities, 598 events, record types, kinds, agent tools) is frozen as of P-PR_33b. Any change needs a lead ruling recorded here and a re-record of the frozen hashes in the same PR. Layout note: tests live under both contracts/tests and packages/contracts/tests; consolidate to packages/contracts/tests in the next packet that touches them.
- 10 | Grok prep failures | Ruling 10: Grok prep packets that failed CI, ownership or the checklist (P-PR_21, 23, 40-42, 51-53) go to Sonnet finishers who start from Grok's branch packet/<id>. UI batch screen tests may live under ui/src/__screens__/** (owned by the UI batch packets). Grok's real success rate on prep is about half; the hour-1 dry run must measure it on build packets before G0 and the Grok/Sonnet split will be re-planned from that number.
- 11 | 0.6 code import | Ruling 11: no bulk import of 0.6 code before the window. The import packets (P-PR_40-42) could only edit their logs, so no code was copied. Each build packet ports exactly the 0.6 files in its reuse_from list, with real types (ruling 2), inside its own owned files. The F12 logs become the port map: every row names the build packet that ports it.
- 12 | CI queue time | Ruling 12: the push budget (5 min) measures execution time from the first job start; queue wait is reported separately and alerts at 2 min. P-PR_52 measured 1m30s of execution and about 4.5 min of queueing on 12 saturated runners. For the build window, add temporary runner hosts on the personal DigitalOcean account (sized by the dry run's measured queue) and destroy them after final testing. Shorten the serial chain (select runs in parallel with golden and contracts).
- 13 | Worker context | Ruling 13: every worker clone carries the spec: V1-SPEC.md, ARCHITECTURE-V1.md, ARCH-DECISIONS.md, CONSOLE-SPEC.md and the rulings export live in docs/spec/ on main (lead-owned, frozen with the contract). The dispatcher puts the full trk brief, the lane brief (docs/lanes/<lane>.md) and the text of every referenced spec section into each prompt. A packet's done check includes a reviewer pass against those sections, not only tests.
