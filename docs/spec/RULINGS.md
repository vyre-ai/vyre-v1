- 62 (amended) | A member's own AI account on a Space server | Owner ruling, 3 Nov 2026 ("its fine to put it encrypted on the server in their own folder ... make it seamless"). Ruling 62 said a Space server holds the key of its owner alone, so no member of a server Space could use their own Claude, ChatGPT or Grok. Now a Space server may hold any person's key in memory while a signed-in session of that person's that handed it over is live: signing in with a password hands it over (POST /vault/key/unlock on the Space's address, https only, never the admin token), sign-out or the end of their sessions drops it. Unchanged: the key opens that person's Mine items for their own turns only, never another person's or an agent's for someone else; it is never written to disk unwrapped, never readable through any API, and its use is logged. When the server does not hold it, the member's turn runs on the Space AI key and the chat says so. Their own computer's daemon still takes it as before. Also (approved by the lead the same day, built in l-memberkey): a wrap of the key that the server opens after a Google, Microsoft or GitHub sign-in, so a member who never types their password is not asked for it. Its two risks, accepted by the owner: (1) the wrap's key lives on the server, so whoever holds the server's disk and that key (the Space's operator, a backup, a stolen machine image) can open every such member's Mine items at any time, signed in or not; (2) whoever controls a member's Google or GitHub identity (for example a Workspace admin who resets that account) can open that member's Mine, including their personal AI sign-ins, not only the Space's data. Mitigations: the wrap is made only while the key is held from a password unlock; its key is a random server secret beside the vault master key, never in the database; it opens only inside the SSO and GitHub sign-in after the provider's proof and binds to the new session; every open is an audit row (who, when, which provider); reset and password change drop it; Vault has "Forget on this server"; an owner can turn it off in Console (Policies > Sign-in requirements, policy vault.open_after_provider_sign_in, on by default), which drops every wrap.

- 3 Nov 2026 (owner) | Personal memory under the person's own key (l-memkeys) | Owner ruling: keep the current words ("Private to you", spec b7) and make them true now, not in a later wave. Personal memory was sealed under a key the server derives from its own seal key (scope mem.<owner>), so the server could read it at rest. Now a person's private memory (person-layer facts, personal pages with their versions and links, personal note titles) is sealed with keys made from their person key, the Mine Vault's family (HKDF of personKey): their own form (AES-256-GCM, "pm1.o") and a public form ("pm1.p", X25519 sealed to a memory public key whose private half is derived from the person key and never stored). Writes need no private key: capture, nightly jobs and agents acting while the person is signed out seal to the public key (memory_person_keys, registered the first time the key is held in that Space). Reads need the key: the server keyring holds it only while a session of theirs that handed it over is alive (R62 amended), their own computer's keyring once unlocked; only their own turns and their own reads ask for it; without it the text reads as empty, and recall, memory_search, facts.list and facts_as_of say why in one plain line (`locked`). Search: the plain text, BM25 words, trigram vectors, meaning vectors and row list of a person's facts live only in process memory while the key is held (built by the background job or on first use, dropped at sign-out); nothing derived from personal text is written to a table. Migration: every 30 s the job memory.personal_keys re-seals each held person's server-sealed and public-form rows to their own form, checks the new value opens to the same words, and overwrites the old value with secure_delete on and a WAL checkpoint; it folds exact duplicates capture wrote while they were out. A person who never signs in again keeps the old server seal until they do; a row under an older person key (a reset without recovery) stays closed, like a Mine item. Rows are chosen by enc = 2, so a fact its owner made public on their profile (l-profile) is left plain. The answer idempotency keeps for a repeated memory write no longer holds personal words (host/src/invoke.ts). Not changed: who sees what; shared and Space memory stay under the Space's keys; engines get personal memory only for the person's own turns. Inherited risk: where the "open after a Google, Microsoft or GitHub sign-in" wrap is on (R62 amended, on by default), whoever holds the server's disk and that wrap key can recover the person key, and so this memory too; turning the policy off in Console closes that. Contract: additive optional `locked` on memory.search, memory.pointer, memory.facts.list and memory.facts_as_of outputs, approved by the lead under ruling 9 on 3 Nov 2026 (snapshots re-recorded by the regen bot).
