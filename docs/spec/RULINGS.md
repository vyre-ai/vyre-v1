- 62 (amended) | A member's own AI account on a Space server | Owner ruling, 3 Nov 2026 ("its fine to put it encrypted on the server in their own folder ... make it seamless"). Ruling 62 said a Space server holds the key of its owner alone, so no member of a server Space could use their own Claude, ChatGPT or Grok. Now a Space server may hold any person's key in memory while a signed-in session of that person's that handed it over is live: signing in with a password hands it over (POST /vault/key/unlock on the Space's address, https only, never the admin token), sign-out or the end of their sessions drops it. Unchanged: the key opens that person's Mine items for their own turns only, never another person's or an agent's for someone else; it is never written to disk unwrapped, never readable through any API, and its use is logged. When the server does not hold it, the member's turn runs on the Space AI key and the chat says so. Their own computer's daemon still takes it as before. Also (approved by the lead the same day, built in l-memberkey): a wrap of the key that the server opens after a Google, Microsoft or GitHub sign-in, so a member who never types their password is not asked for it. Its two risks, accepted by the owner: (1) the wrap's key lives on the server, so whoever holds the server's disk and that key (the Space's operator, a backup, a stolen machine image) can open every such member's Mine items at any time, signed in or not; (2) whoever controls a member's Google or GitHub identity (for example a Workspace admin who resets that account) can open that member's Mine, including their personal AI sign-ins, not only the Space's data. Mitigations: the wrap is made only while the key is held from a password unlock; its key is a random server secret beside the vault master key, never in the database; it opens only inside the SSO and GitHub sign-in after the provider's proof and binds to the new session; every open is an audit row (who, when, which provider); reset and password change drop it; Vault has "Forget on this server"; an owner can turn it off in Console (Policies > Sign-in requirements, policy vault.open_after_provider_sign_in, on by default), which drops every wrap.

- 3 Nov 2026 (owner, about 04:05 PKT) | The setup grant for outside agents | Owner ruling: "can you make it so that in future versions, you or someone else's claude code or codex are able to make changes and connect everything ... there are blockers by design. - 3 Nov 2026 (owner, about 05:45 PKT) | AI tools on the open internet (l-openweb) | Owner ruling: "They will ofcourse be able to use the internet right? and do everything that they normally can do in claude code and codex apps etc". CLI engines (Claude Code, Codex, Grok) reach any public host by default, on any port, through the sandbox's egress proxy: Claude Code's WebFetch, git over HTTPS, git over SSH (tunnelled through the proxy), npm, pip, cargo, go modules, Homebrew downloads and curl work with no setup, because the sandbox sets the proxy variables those tools read. Never reachable whatever the setting: loopback, private, link-local and cloud metadata, carrier-grade NAT, multicast and reserved addresses, this machine's own addresses and the networks it sits on (the person's LAN), and Vyre's own ports; a name is resolved once and the connection goes to the checked address. The rule is one plain-JSON value (sandbox/src/egress-policy.ts, `{ egress: "public" }` or `{ egress: "list", allow }`) built in one place (modules/engine/sandbox-default.ts wallEgress), shared with the Windows WSL2 sandbox. Owners and admins can tighten it in Console, AI, Internet access (setting engine.egress): "Anything public (default)", "Only the AI providers" (the old behaviour), or "A list I choose". It applies when each engine process starts, on the Space's servers and on members' computers for that Space. Every refusal is an audit row (engine.egress_denied, class deny); a turn's details list the hosts it reached. Filesystem confinement is unchanged.
- 3 Nov 2026 (owner, about 06:10 PKT) | What a CLI engine may touch on files and in the terminal (l-openweb) | Owner ruling: "Personal is personal and everything goes zero friction... folders you select from your computer to be available in Vyre. So it cannot get access to the folder that contains vyre's secrets etc and always has to go through vyre. And on space, it should have access to workspace and any folders or repos mounted to the workspace and if its running on my computer for the space then any folders the space has mounted or I choose to mount private to myself... Terminal needs to be open for large part so nothing is blocked and git commands too". And: "In personal space, it needs to be able to install packages and things in your computer using terminal too ... unblocked completely that way, and team space should come with those things too". The model: on the person's own computer the engine reads and writes the chat's workspace and every folder the person added to Vyre (and, for a Team Space, that Space's mounts and the person's private mounts in it), its own CLI config, the user-level package locations (Homebrew, npm, pip --user, cargo, go, nvm and the like) so installs work, reads the toolchains, ~/.gitconfig and ~/.ssh/known_hosts, and uses SSH through the agent socket; it never reads Vyre's data folder (Vault, databases, keys), private key files, other apps' credential stores or browser profiles, or the rest of the home folder. A command that needs admin rights shows the person the Terminal card to run it themselves. On a Space server the engine sees only that Space's workspace and mounts, and installs land in the Space's own persistent toolbox, never on the host. The mount list comes from one builder, read at each turn start.
