# Console infrastructure and private administrative exports

The Server, Diagnostics and Support pages use live capabilities. Log exports and support bundles now have actual encrypted content rather than an ID without a downloadable file. Service restart feedback says requested; the health service remains the authority for observed state.

## Authorization and retention

Only the daemon wrappers for `logs.export`, `health.support_bundle` and `audit.export` receive an export port. They accept handler-generated structured metadata (or the audit handler's fixed CSV format), with no destination, target principal or arbitrary file-write port. The daemon captures principal kind and ID, trace and acting-for person. Effective requester ownership includes both kind and ID; actor and on-behalf-of attribution remain separate.

The handler still passes normal capability authorization. A private file resource is registered through `resource.created`; normal `files.get`/`files.read` resource authorization still runs before the host wrapper resolves the artifact. The wrapper additionally requires the exact effective requester and their current source permission (`server.logs` or `audit.read`). Even another Owner cannot read it. The encrypted blob has no public resource binding. Browser downloads use authenticated `files.read` base64 and a revocable browser Blob URL.

Exports are scrubbed recursively with the existing credential sanitizer and content-key exclusions, capped at 8 MiB, and expire after 24 hours. Cleanup runs at boot, every minute, before saves and before reads. It removes encrypted bytes, private artifact metadata and the corresponding log/support cache copy. Audit resource metadata remains; artifact content does not. Expiration does not recall copies that a requester already downloaded.

## Evidence and limits

Booted HTTP tests exercise a role with only server.logs and Space view, no Files write: export, normal file metadata, base64/text/URL reads, cross-person denial, missing permission, no port on unrelated capabilities, and unchanged ordinary Files create denial. Unit tests cover same ID with a different principal kind, acting-for ownership, scrubbing, bounds and expiration cleanup. Console Chromium tests perform owner claim, standalone Console navigation, filtered log export, actual browser download, health checks, support export and JSON content verification.

The browser run exposed a shutdown race: late callbacks scheduled a LogSink flush after its database closed. Close now drains every accepted row/span once, and late append/flush/repeated close calls are harmless. A persistent-database regression verifies both accepted records survive and late records do not enter storage.

The second slice adds Updates, Backups destination/schedule/encryption controls, deletion review and Space identity/ownership controls. Storage currently exposes real machine, disk and encryption probes; no contract exists for volume management. No real update, restore or service restart is performed by these browser tests. A pre-midnight production export reproduced React #418 on initial /claim and /console hydration before any infrastructure page mounts. A fresh same-day export passes all three Chromium tests with zero page errors, including profile persistence after reload, backup target save and ZIP download. Root owns the deterministic Welcome greeting correction needed for cross-day SSR.


## Owner Space archives and transfer

`backup.export_status` is additive: input `runId`; output `state: ready`, `fileId`, `name`, `sizeBytes`, `expiresAt`. It returns no ready state before the encrypted ZIP is written and read back byte-for-byte. Missing/not-finished/expired archives fail explicitly. The separate owner archive port exists only during `backup.export_start` and status execution; it is not the metadata export port. Both source permissions (`server.backups` and `records.export`) and the current active person owner are checked before generation, after persistence, on status and on every Files read. Acting-for access is refused. Requester and current owner must still match; a new owner cannot inherit an earlier requester's archive. ZIPs expire after24hours, are capped at256MiB, and are read only as authenticated base64 chunks of at most1MiB. Console assembles these chunks before creating a local download URL.

The real HTTP owner export originally failed because its extra authorization targeted a null Space ID. It now targets ctx.space. Transfer also used invalid plain role IDs and never updated the Space resource owner. Transfer now validates the current owner and active person target without making separate role mutations; one durable ownership event changes the Space resource and both role assignments together. Invalid/stale events do nothing. The projection follows the same rule on restart. Current access ownership takes precedence over the bootstrap owner setting. HTTP regression proves the new resource owner, new Owner/old Admin roles, restart persistence and old/new requester archive denial. Failed HTTP deletion previously left deleted_at set; host refusal now occurs before any local tombstone or event.

Remaining contract gaps stay explicit: the existing export source supplies shared Space history plus README, not full Files, chats and settings content. The UI says this rather than claiming a full export. Full safe content projection remains required v1 work. Space deletion is server-command-line-only in the current host seam; the UI exposes that limitation. Address updates persist the profile; actual relay/domain reconciliation belongs to Network and is not proven by this slice. The local fresh fixture lacks the installed vyre-server command, so Updates displays its unavailable state; update driver unit/integration coverage does not establish a real deployment update. No real update, rollback, service restart, live restore or deletion was performed.
