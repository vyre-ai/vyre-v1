# Spike S13: vectors and embeddings (ARCH R14)

Ran on the v1-perf runner (cores to itself, ruling 46), node v24.22.1, run 40209183278 on commit e2d35586. Budgets are acceptance, not targets. Nothing ran on the Mac.
(Path: this file lives in spikes/s13/ because the packet owns spikes/s13/**; the checklist names spikes/S13.md.)

## Brute-force cosine over 200,000 vectors of 384 dimensions

| Path | Runs (ms) | Median | Budget | Verdict |
|---|---|---|---|---|
| Plain JavaScript scan, float32 (VectorIndex.top with jsKernel) | 338.9, 339.6, 329.5, 343.2, 338.7 | 338.9 | 60 | miss, as expected |
| First SIMD kernel, float32, vectors in kernel memory, scan only | 57.2 to 60.9 | 59.6 | 60 | passed by 0.4 ms: memory-bandwidth bound (about 5 GB/s over 307 MB) |
| First SIMD kernel through VectorIndex.top | 62.6, 66.5, 66.3, 63.5, 68.0 | 66.3 | 60 | miss |
| **int8 store through VectorIndex.top (the production path)** | 28.4, 29.6, 28.6, 27.7, 30.8 | **28.6** (worst 30.8) | 60 | **pass** |

The int8 store (ruling from the lead): each unit vector is kept as 384 int8 with a per-vector scale in WebAssembly memory, scanned by `dot8` (kernel.wat, assembled on the runner by wabt: `v128.load8x8_s` widens, `i32x4.dot_i16x8_s` against an int16 query). The best 200 by int8 score are reranked exactly with the float32 copy and the top 20 returned.

- Recall@20 against the exact JavaScript scan: **1.0000** over 20 queries; the top 20 was identical, in order, on 20 of 20 (the fixed query 987654 included).
- Memory per 200,000 vectors: int8 73 MB + scales 1 MB + float32 for the rerank 293 MB = **367 MB** (the plain float32 index is 293 MB). Measured rss growth after loading both indexes was 689 MB.
- The kernel source is readable WAT (spikes/s13/kernel.wat); no hand-encoded bytes. The assembled bytes are what kernel.test.ts exercises.

## Embeddings: all-MiniLM-L6-v2, quantized ONNX (ruling 47: Xenova/all-MiniLM-L6-v2 at revision 751bff37, sha256 pinned in model.ts)

| Runtime | Setting | Chunks per second (200 chunks of about 380 characters) | Budget | Verdict |

| onnxruntime-node (the host, ruling 54) | 1 thread (the perf runner reports 2 cores, so cores - 1), batches of 32 by length | 28.9, 29.3, 32.0 | 100 | **miss** (about 3.4x short); model load 809 ms |

Quality: unit length 1.0000; a related pair 0.730, an unrelated pair 0.024.

Run 40220073896 (commit after b1a4fc11). Web, 1 thread: 9.1, 10.0, 9.6. Host vs web parity on the fixed eight texts: worst cosine **0.959** against the required 0.999 (**fail**; which text differs is not yet known, a suspect is the empty string or the 600-character text cut at 128 tokens). The VectorIndex.top median in this run was 28.3 ms.

Ruling 54: the host embeds with onnxruntime-node; clients keep the WASM runtime. The host vectors must match the web vectors within 1e-3 cosine on a fixed set of eight texts (bench.ts checks the worst cosine and fails under 0.999).

## Decisions

- The vector scan is int8 with an exact float32 rerank; the kernel owns vector storage behind `VectorKernel.store` in modules/search/projections.ts; the plain JavaScript path stays the default and the reference.
- sqlite-vec is not needed at 200k vectors.
- The web WASM embedder does not reach 100 chunks per second; the host path is native.
